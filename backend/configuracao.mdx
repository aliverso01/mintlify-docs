## CORS / CSRF

- `CORS_ALLOW_ALL_ORIGINS` (`core/settings.py:40-47`): calculado a partir de `CORS_ALLOWED_ORIGINS` (env, CSV). Se o valor for só `*` (default), libera todas as origens; caso contrário, restringe à lista informada.
- `CSRF_TRUSTED_ORIGINS` (`core/settings.py:49-67`): default `http://localhost:5173`. O código normaliza cada origem (garante esquema `https://` quando ausente) e adiciona automaticamente a variante `http://` para origens `localhost`/`127.0.0.1`.
- Em produção (`DEBUG=False`): `CSRF_COOKIE_SECURE=True`, `SESSION_COOKIE_SECURE=True`, `SECURE_PROXY_SSL_HEADER=('HTTP_X_FORWARDED_PROTO', 'https')` (para confiar no HTTPS terminado pelo Traefik), `SECURE_REFERER_POLICY='strict-origin-when-cross-origin'` (`core/settings.py:81-91`).
- `USE_X_FORWARDED_HOST = True` (`core/settings.py:79`) — necessário atrás de proxy reverso.

## Arquivos estáticos e media

- `STATIC_URL='static/'`, `STATIC_ROOT=BASE_DIR/'static'` — servidos por WhiteNoise (`CompressedManifestStaticFilesStorage`) tanto com quanto sem S3 (`core/settings.py:260-300`).
- **Media**: controlado por `USE_S3` (env, default `False`).
  - `USE_S3=True`: usa `storages.backends.s3boto3.S3Boto3Storage`. Exige `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_STORAGE_BUCKET_NAME`; `AWS_S3_REGION_NAME` (default `us-east-1`), `AWS_S3_CUSTOM_DOMAIN` e `AWS_S3_PROJECT_FOLDER` (default `miggo-backend`) ajustam a URL final. `AWS_QUERYSTRING_AUTH=False` e `CacheControl: max-age=86400` fixos no código.
  - `USE_S3=False`: `FileSystemStorage`, `MEDIA_ROOT=BASE_DIR/'media'`, `MEDIA_URL='/media/'`.
- Em produção sem Nginx, `core/urls.py:55` serve `/media/<path>` via `django.views.static.serve` diretamente do Django.

## Cron (django-crontab)

`CRONJOBS` (`core/settings.py:374-377`) tem uma única entrada:
```python

```
O comentário no código (`core/settings.py:369-373`) explica que os jobs de cobrança (trial/faturas/reconciliação Stripe) **não** ficam aqui — rodam como management commands agendados externamente (Dokploy). Duas entradas antigas usavam formato de 6 campos (`*/30 * * * * *`), que o crontab do Linux recusa, e nunca chegaram a rodar em produção.

## Logging

Bloco extenso (`core/settings.py:382-480`) motivado por um bug histórico: sem configuração de `LOGGING`, o Django não instala handler nenhum para os loggers da aplicação, e todo `logger.info(...)` do onboarding era descartado em silêncio.

- `LOG_LEVEL` (env, default `INFO`) controla o nível do logger `app` (raiz de todos os apps do projeto) e do console.
- `DJANGO_LOG_LEVEL` (env, default `INFO`) controla o logger `django` separadamente.
- `LOG_FILE` (env, opcional): se preenchido, adiciona um `RotatingFileHandler` (10MB, 5 backups, UTF-8) a todos os loggers, além do console. Antes de registrar o handler, o código testa se consegue abrir o arquivo para escrita — se não conseguir, cai de volta para console-only com um aviso em `stderr`, em vez de derrubar o processo.
- Loggers de bibliotecas HTTP (`urllib3`, `requests`, `PIL`) ficam fixos em `WARNING` para não afogar o log com ruído de DEBUG.
- Um ajuste específico reconfigura `sys.stdout`/`sys.stderr` para UTF-8 com `errors='backslashreplace'` (`core/settings.py:410-415`) — o console do Windows abre em `cp1252` e trocava acentos por `?`.
