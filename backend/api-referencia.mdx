## Schema OpenAPI (drf-spectacular)

| Rota | O que é |
|---|---|
| `GET /api/schema/` | JSON/YAML do schema OpenAPI (`SpectacularAPIView`) |
| `GET /api/schema/swagger-ui/` | UI interativa Swagger |
| `GET /api/schema/redoc/` | UI Redoc |

Config em `SPECTACULAR_SETTINGS` (`core/settings.py:159-164`): título "Miggo API", versão "1.0.0". `DEFAULT_SCHEMA_CLASS='drf_spectacular.openapi.AutoSchema'` está em `REST_FRAMEWORK` (`core/settings.py:147`), então toda view DRF entra automaticamente no schema.

## Webhooks

<AccordionGroup>
  <Accordion title="POST /webhooks/ — Stripe">
    `webhook_stripe` (`app/webhooks/views.py:62`). Sem autenticação DRF (`permission_classes=[]`) — a validação é a assinatura HMAC do header `Stripe-Signature`, conferida contra `STRIPE_WEBHOOK_SECRET` via `stripe.Webhook.construct_event`. Sem o secret configurado, recusa com `503`.

    Idempotência via `StripeEvent.event_id` (único) — reenvio da Stripe vira no-op (`200 already_processed`). Eventos tratados (`HANDLED_EVENTS`, `app/webhooks/views.py:33-46`): `checkout.session.completed`, `checkout.session.async_payment_succeeded/failed`, `customer.subscription.created/updated/deleted`, `customer.subscription.trial_will_end`, `invoice.created`, `invoice.finalized`, `invoice.paid`, `invoice.payment_succeeded`, `invoice.payment_failed`. Demais tipos são reconhecidos com `200 ignored_event` (para a Stripe não reenviar) e apenas logados.

    Erro no handler: processa dentro de `transaction.atomic()`; se falhar, apaga o `StripeEvent` recém-criado (libera retentativa) e responde `500` — a Stripe reenvia automaticamente.
  </Accordion>

  <Accordion title="POST /webhooks/zernio/account/ — Zernio/GetLate">
    `webhook_zernio_account` (`app/webhooks/views.py:417`). Sem autenticação DRF. Só trata o evento `account.connected`: localiza a `PlatformIntegration` pendente por `profile_id` (+ `platform`, quando resolvido) e ativa (`status='active'`), notificando o cliente. Demais eventos são apenas logados em `Integration`.
  </Accordion>

  <Accordion title="POST /webhooks/manychat/">
    `webhook_manychat` (`app/conversation/webhooks.py:42`). Sem autenticação DRF — validado por um token compartilhado lido do header, comparado contra `MANYCHAT_WEBHOOK_TOKEN` (`app/conversation/webhooks.py:27`).
  </Accordion>

  <Accordion title="POST /webhooks/manychat/dynamic-block/continue/">
    `manychat_dynamic_block_continue` (`app/conversation/webhooks.py:90`). Sem autenticação DRF. URL fixa do flow casca (`ConversationFlowState` decide o que renderizar — nunca um parâmetro da URL, conforme comentário em `core/urls.py:50-53`).
  </Accordion>
</AccordionGroup>

## Convenções de resposta e erro

- **Paginação**: `StandardPagination` (`utils/pagination.py`) — `PageNumberPagination` com `page_size` default 10, parametrizável via `?page_size=` restrito a `[10, 30, 50, 100]` (`ALLOWED_PAGE_SIZES`). Resposta paginada: `{"count", "next", "previous", "results"}`. Não confirmado se todas as `ListAPIView` usam essa classe globalmente (`REST_FRAMEWORK` em `core/settings.py` não define `DEFAULT_PAGINATION_CLASS`) — verifique a `pagination_class` de cada view específica.
- **Filtros**: `DEFAULT_FILTER_BACKENDS` global inclui `DjangoFilterBackend`, `SearchFilter` e `OrderingFilter` (`core/settings.py:142-146`) — views de listagem podem aceitar `?search=`, `?ordering=` e filtros de campo conforme `filterset_fields`/`filterset_class` de cada view.
- **Erros**: não há um formato de erro global customizado (`EXCEPTION_HANDLER` não é sobrescrito) — segue o padrão DRF (`{"detail": "..."}` ou mapa de erros por campo em validação de serializer). Várias views próprias retornam `{"message": "..."}` em vez de `{"detail": "..."}" (ex.: `LoginView`, `GoogleAuthView`) — não é uniforme entre apps.
- **Autenticação**: ver [Autenticação](/backend/autenticacao). Permissão padrão de toda rota não sobrescrita: `HasAPIKeyOrIsAuthenticated`.
