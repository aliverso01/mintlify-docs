## Responsabilidade

O app `app.notification` guarda e expõe as notificações in-app da Miggo: eventos como novo post, aprovação de conteúdo, cobrança, onboarding etc. viram registros de `Notification` associados a um `CustomUser` (`app/notification/models.py:47`). Não há disparo por push/e-mail aqui — é só persistência e leitura; quem decide **quando** notificar é o código de outros apps, que chama as funções utilitárias expostas em `app/notification/utils.py`.

O app está registrado em `INSTALLED_APPS` como `app.notification.apps.NotificationConfig` (`core/settings.py:128`) e montado em `core/urls.py:40` sob o prefixo:

```
/api/v1/notification/
```

<Note>
Este app não tem `admin.py` — não há registro no Django Admin para o model `Notification`.
</Note>

**`get_created_at_relative(obj)`** (`serializers.py:19-37`): calcula o tempo relativo até `timezone.now()` e retorna string em pt-BR:
- `< 1 min` → `"Agora"`
- `< 1 hora` → `"há {N} min"`
- `< 1 dia` → `"há {N}h"`

## Regras de negócio e funções

`app/notification/utils.py` concentra as duas funções públicas usadas por **outros apps** para gerar notificações. Não há signals no app — a criação é sempre uma chamada explícita a uma destas funções.

### `notify(recipient, notification_type, title, message, link=None)`

`app/notification/utils.py:5-25`

- **Assinatura:** `recipient: CustomUser`, `notification_type: str`, `title: str`, `message: str`, `link: str = None`.
- **Efeito colateral:** cria um único `Notification` via `Notification.objects.create(...)` (`utils.py:19-25`).
- **Retorno:** nenhum (retorno implícito `None`).
- **Uso documentado no próprio docstring:**
  ```python
  from app.notification.utils import notify
  notify(user, 'new_post', 'Novo post', 'Um post foi criado para...', '/content')
  ```

### `notify_admins(notification_type, title, message, link=None, dedupe_window_seconds=0, dedupe_key=None)`

`app/notification/utils.py:28-66`

- **Assinatura:** `notification_type: str`, `title: str`, `message: str`, `link: str = None`, `dedupe_window_seconds: int = 0`, `dedupe_key: str = None`.
- **Efeito colateral:** cria uma `Notification` para **todos** os `CustomUser` com `role='admin'` e `is_active=True` (`utils.py:55`), em lote via `Notification.objects.bulk_create(...)` (`utils.py:66`).
- **Deduplicação opcional:** se `dedupe_window_seconds > 0` e `dedupe_key` for informado, antes de criar verifica se já existe uma `Notification` do mesmo `notification_type` cujo `message` contenha `dedupe_key` dentro da janela `now() - dedupe_window_seconds`; se existir, a função retorna sem criar nada (`utils.py:43-53`). Serve para não gerar uma notificação por admin a cada upload de um lote de mídias, por exemplo.
- **Retorno:** nenhum (`None`).

<Note>
As buscas em `app/notification` e `app/account` não localizaram nenhum outro ponto do próprio app que chame `notify`/`notify_admins` — os chamadores ficam em outros apps (post, media, subscription, conversation, etc.), fora do escopo desta página.
</Note>

## Erros comuns / pontos de atenção

<Warning>
`NotificationMarkReadView.patch` (`views.py:120-128`) não verifica se a notificação pertence ao `user_id`/usuário autenticado — apenas busca por `pk`. Qualquer chamada autenticada com um id válido marca a notificação como lida, mesmo que seja de outro usuário.
</Warning>

<Warning>
`NotificationMarkAllReadView.patch` não valida se `user_id` corresponde a um usuário existente — um id inválido simplesmente atualiza zero linhas e responde `{'success': true}` do mesmo jeito, sem sinalizar o problema ao cliente.
</Warning>

<Warning>
O filtro `client_id` em `NotificationHistoryView` (`views.py:80-85`) depende de o `client_id=<id>` aparecer como texto dentro de `message` ou `link` — não há uma FK direta de `Notification` para `Client`. Se o texto da notificação for escrito sem esse padrão, o filtro simplesmente não encontra o registro.
</Warning>

<Note>
Nenhuma view pagina/filtra por `notification_type` inválido de forma diferenciada — um valor fora de `NOTIFICATION_TYPES` apenas resulta em zero resultados, sem erro.
</Note>
