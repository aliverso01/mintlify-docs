## Responsabilidade

O app `post` é o coração operacional da plataforma Miggo: modela o **conteúdo** que a equipe produz para os clientes (`Post`), o **formato** e a **rede social** de destino, o **fluxo de aprovação** (status + histórico de transições), a **mídia vinculada** a cada post, as **integrações de plataforma** (Instagram/LinkedIn via Zernio/Late.dev e WhatsApp via ManyChat) e os **insights de performance** sincronizados do Zernio.

É consumido por:
- **Frontend** (Kanban de conteúdo, tela "Meus conteúdos" do cliente, configurações de integração, dashboard de insights, tela "Minha Marca").
- **Webhooks externos**: Zernio (`webhook-update-post/`, `webhook-account-connected/`) e o link permanente de mídia aberto pelo cliente via WhatsApp.
- **ManyChat/conversas** (`app.conversation`): dispara automações (envio para aprovação, "pode postar", aviso de publicação) e consulta o link de mídia de um post (`PostMediaLinkView`).
- **Cron** (`app/post/cron.py`): processa revisões agendadas (`ScheduledReview`).
- **`app.editorial_calendar`**: `Post` referencia `EditorialCalendar` (origem da pauta) e o serializer usa `FormatStyleRule`/`rules_for_post` para anexar regras editoriais.
- **`app.media`**: cada `MediaPost` vincula um `Post` a uma `Media`.

## Regras de negócio e funções

### `app/post/signals.py`
Escuta `pre_save`/`post_save` de `Post` para gravar `PostStatusEvent` automaticamente, cobrindo qualquer caminho de código que use `.save()` (aprovação do cliente, publicação, cron do Zernio, correção via WhatsApp) sem precisar instrumentar cada um.

- `remember_previous_status(sender, instance, **kwargs)` (`app/post/signals.py:15-26`, `pre_save`): antes de gravar, busca o status **anterior** direto do banco (`Post.objects.filter(pk=instance.pk).values_list('status__name', flat=True).first()`) e guarda em `instance._previous_status_name` — necessário porque no `post_save` a linha já estaria atualizada.
- `record_status_event(sender, instance, created, **kwargs)` (`app/post/signals.py:29-44`, `post_save`): se o post tem status atual e (foi criado OU o status mudou), cria um `PostStatusEvent`. Não faz nada se `current` for vazio (post sem status) ou se o status não mudou num update.

### `app/post/stalled.py`
- `stalled_posts(queryset=None, min_days=0, only_active_clients=True)` (`app/post/stalled.py:23-38`): retorna posts com `status__name='sent'` (constante `STALLED_STATUS`), opcionalmente só de clientes ativos, ordenados por `updated_at` crescente (mais antigo primeiro). `min_days=0` retorna a fila inteira de espera. ### `app/post/media_link.py` — link permanente de mídia (MIG-235)
Resolve um bug em que o link de mídia enviado ao cliente pelo WhatsApp "andava" para o post mais recente, porque dependia de um campo customizado do subscriber no ManyChat que é sobrescrito a cada novo envio.

- `build_media_view_token(post_id: int) -> str` (`app/post/media_link.py:22-24`): assina `post_id` com `django.core.signing.Signer(salt='post-media-view')` — token permanente, amarrado ao post, não ao cliente/subscriber.

- `guess_content_type(filename: str) -> str` (`app/post/media_link.py:59-61`): mapeia extensão → content-type via `MEDIA_CONTENT_TYPES` (mp4, mpeg, mov, avi, webm, jpg/jpeg, webp, png, gif, pdf); fallback `application/octet-stream`.

### `app/post/services.py`
- `send_post_for_approval(post)` (`app/post/services.py:47-153`): regra central de envio de post para aprovação via WhatsApp — usada tanto pela view HTTP `SendPostWhatsAppView` quanto por uma ação de flow do módulo de conversas. Passos, na ordem (a ordem importa):
  1. Valida `post` existente e com `post_format`.
  2. Localiza `PlatformIntegration` WhatsApp do cliente com `profile_id`.
  3. Grava/atualiza `PostMetadata` `whatsapp_media_view_url` com o link permanente da primeira mídia vinculada (se houver).
  4. Grava `post_id` no custom field do ManyChat (`setCustomField`, `field_id=12805782`) — **antes** de disparar o flow, porque é dali que o flow lê qual post está em aprovação.
  5. Só marca `post.status = PostStatus 'sent'` depois que o passo 4 confirma sucesso.
  6. Dispara o flow de aprovação (`sendFlow`, `flow_ns=CONTENT_APPROVATION_FLOW_ID`) e registra o log em `conversation_services.log_automation`.
  
  Retorna `(ok: bool, payload: dict, http_status)`.

<Warning>
`app/post/services.py:153` retorna `'media_view_url': media_view_url` na resposta de sucesso, mas essa variável **nunca é atribuída** em nenhum ponto da função (o valor calculado no passo 3 é salvo só em `PostMetadata`, sem ficar numa variável local `media_view_url`). Isso causa `NameError` sempre que `send_post_for_approval` completa com sucesso — tanto via `SendPostWhatsAppView` quanto via a ação de flow de conversa. Reportado como inconsistência de código, não corrigido aqui.
</Warning>

## Erros comuns / pontos de atenção

- **`send_post_for_approval` tem um `NameError` garantido no caminho de sucesso** (`app/post/services.py:153`) — `media_view_url` é referenciada mas nunca atribuída. Afeta `SendPostWhatsAppView` e a ação de flow de conversa equivalente.
- **Rotas de edição/exclusão de formato e status são, na prática, apenas listagem** (`app/post/urls.py:18-19,24-25`) — `format/edit/`, `format/delete/`, `status/edit/`, `status/delete/` todas mapeiam para as views de list, não para update/delete.
- **`read_only_fields` de `PlatformIntegrationSerializer` referencia campos inexistentes** (`hash`, `user` — `app/post/serializers.py:192`), sem efeito funcional mas indício de código desatualizado.
- **Mojibake em `PlatformProfileConfigSerializer._display`** (`app/post/serializers.py:288`): separador de `cover`/`banner` corrompido (`â€”` em vez de `—`).
- **`webhook-update-post/` e `webhook-account-connected/` são públicos sem verificação de assinatura/token** do lado do Zernio — diferente de `PostMediaLinkView`, que exige um token compartilhado.
- **`PostStatus.name` é texto livre, sem `choices`** — todo o fluxo de negócio (publicação, notificações, escopo do cliente, fila de parados) depende de comparações por string (`'published'`, `'sent'`, `'scheduled'` etc.); um nome de status cadastrado incorretamente no banco quebra silenciosamente essas comparações.
- **`PostListView` só pagina quando `?stalled_days=` está presente** — a listagem padrão do Kanban não é paginada; pode crescer sem limite se usada fora do padrão de "semana" esperado pelo frontend.
- **Publicação/webhook rodam em threads de background "soltas"** (`threading.Thread(daemon=True)`, sem fila/worker dedicado) — falhas são apenas logadas via `print`, sem retry automático nem alerta estruturado; `webhookUpdatePostView._process_webhook` faz polling de até 10s por `PostMetadata` antes de desistir silenciosamente.
- **Views classes `SendApprovationWhatsappView` e `WebhookPostPublishView`** existem no código mas não estão roteadas — a segunda tem `post()` sem `return`.
