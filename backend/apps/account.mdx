## Responsabilidade

O app `account` concentra tudo relacionado a identidade e acesso na Miggo: o modelo de usuário customizado (`CustomUser`, sem `username`, login por e-mail), autenticação por sessão e por JWT (`rest_framework_simplejwt`), login social com Google, cadastro/gestão de clientes e de membros da equipe (admin/gestor), recuperação de senha por código, verificação de e-mail e um par de metadados livres por usuário (`UserMeta`, ex.: código de reset de senha).

Também vive aqui o subsistema de **suporte**: um chat com IA (proxy para a OpenAI, com prompt de sistema fixo no servidor) e tickets de suporte humano, com integração unidirecional Miggo → Jira (projeto `MIG`) para abrir e acompanhar issues.

O app é consumido pelo `frontend-miggo` (login, cadastro, perfil, chat de suporte, formulário de contato, painel administrativo de equipe/tickets) e dispara efeitos em outros apps do backend: ao criar um `CustomUser`, um signal cria automaticamente o `Client` correspondente (`app.client.models.Client`); o serviço de e-mail de "post publicado" (`send_post_published_email`) é pensado para ser chamado pelo `app.post`; e as notificações de resposta de suporte usam `app.notification.utils.notify`.

## Regras de negócio e funções

### Geração e validação de senha (`app/account/serializers.py`)
- `generate_secure_password(length=12)` (linha 12) — gera senha aleatória com `secrets.choice`, garantindo ao menos 1 maiúscula, 1 minúscula e 1 dígito.
- `validate_password_strength(password)` (linha 23) — exige mínimo 8 caracteres, 1 maiúscula e 1 dígito; levanta `serializers.ValidationError` com lista de mensagens em pt-BR.

### Autenticação (`app/account/authentication.py`)
`JWTAuthentication(SessionAuthentication)` (linha 4) — apesar do nome, é uma `SessionAuthentication` com `enforce_csrf` neutralizado (`return` sem validar), necessária para chamadas via `fetch`/`axios` do frontend sem token CSRF.

<Warning>
Em `app/account/views.py`, a classe `JWTAuthentication` do próprio app (`.authentication.JWTAuthentication`, linha 14) é importada e imediatamente sobrescrita pela `JWTAuthentication` real do `rest_framework_simplejwt` (linha 15), que tem o mesmo nome. Isso torna o import da linha 14 um no-op — nenhuma view em `views.py` usa a `JWTAuthentication` local do app diretamente pelo nome.
</Warning>

### Permissões (`app/account/permissions.py`)
- `is_management_user(user)` (linha 15) — `True` para superuser, staff, ou `role in ('admin', 'manager')`.
- `is_admin_user(user)` (linha 26) — `True` para superuser, staff, ou `role == 'admin'` (gestor **não** conta como admin pleno).
- `HasAPIKeyOrIsAuthenticated` (linha 5) — permite acesso via API key de serviço OU usuário autenticado.
- `IsManagementUser` (linha 37) — aceita API key OU `is_management_user`; mensagem `"Acesso restrito à equipe Miggo."`.
- `IsAdminUser` (linha 52) — aceita API key OU `is_admin_user`; mensagem `"Acesso restrito a administradores."`.

### Signal `manage_client` (`app/account/signals.py:7`)
Conectado a `post_save` de `CustomUser` (via `get_user_model()`).
- **Criação (`created=True`):** cria um `Client` (app `client`) com `name`/`email`/`phone` do usuário e `active=True`, e um `ClientMeta` com `key='activation_code'` gerado por `utils.toolkit.generate_code()`.
- **Exclusão (`kwargs.get('deleted')`):** se o `CustomUser` tiver `client` associado, deleta o `Client`. (Nota: `post_save` não emite `deleted=True` nativamente — este ramo depende de algum chamador passar esse kwarg explicitamente; não foi possível confirmar de onde.)
- **Atualização:** sincroniza `name`/`email`/`phone` do `Client` existente a partir do `CustomUser` salvo.

### Integração com Jira (`app/account/jira_service.py`)
Integração **unidirecional** Miggo → Jira via HTTP puro (`urllib`, sem dependência de `requests`), autenticação Basic (e-mail + API token). Configuração lida de `settings.JIRA_BASE_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN`, `JIRA_PROJECT_KEY` (default `'MIG'`) e `JIRA_ISSUE_TYPE` (default `'Suporte'`). Se alguma credencial obrigatória faltar, as funções fazem no-op (retornam `None`/`False`) sem levantar exceção.
- `_config()` (linha 28) — monta a tupla de config ou `None`.
- `_issue_type()` (linha 39) — tipo de issue usado para todo ticket vindo do Miggo.
- `_auth_header(email, token)` (linha 44) — monta o header `Authorization: Basic ...`.
- `_request(method, url, email, token, body=None)` (linha 49) — executa a chamada HTTP e retorna `(status_code, json_ou_dict_vazio)`.
- `_log(service_response, status_code, payload, client=None)` (linha 68) — grava a chamada em `app.integration.models.Integration` (best-effort; qualquer exceção é engolida).
- `_adf_description(ticket)` (linha 85) — monta a descrição do issue no formato Atlassian Document Format a partir dos dados do ticket.
- `create_jira_issue(ticket)` (linha 103) — cria o issue (`project`, `issuetype`, `summary` truncado a 255 chars, `description` em ADF, `priority` mapeada por `PRIORITY_MAP`). Retorna `(key, url)` ou `None`; nunca levanta.
- `update_jira_priority(issue_key, priority)` (linha 144) — `PUT` na prioridade do issue existente. Retorna `bool`; nunca levanta.
- `get_jira_issue_status(issue_key)` (linha 167) — `GET` do campo `status`; retorna `{'name': ..., 'category': ...}` ou `None`; nunca levanta.
- `PRIORITY_MAP` (linha 20) — mapeia prioridade Miggo (`low`/`medium`/`high`/`urgent`) para nome de prioridade padrão do Jira (`Low`/`Medium`/`High`/`Highest`).

### `send_post_published_email(post)` (`app/account/support_views.py:585`)
Utilitário para ser chamado por `app/post/views.py` quando um post muda para status publicado (documentado no próprio docstring como ponto de integração, não é uma view). Busca `post.client.user`, monta contexto com nome do cliente, título, plataforma (via `post.metadata.first()`) e data agendada, e envia e-mail com o template `emails/post_published.html`. Toda a função está envolvida em `try/except` amplo — qualquer erro é logado via `print` e engolido, nunca propaga.

### Django Admin (`app/account/admin.py`)
`CustomUserAdmin(UserAdmin)` usa `CustomUserCreationForm`/`CustomUserChangeForm` (`app/account/forms.py`) para contornar o campo `username` que o `UserCreationForm` padrão do Django exige. `list_display` mostra `email, name, phone, role, is_active, is_staff`; `list_filter` por `role, is_active, is_staff`; busca por `email, name`. `UserMeta` é registrado sem customização (`admin.site.register(UserMeta)`).

## Erros comuns / pontos de atenção

- **`SafeTokenRefreshView`** (`app/account/views.py:224`) existe especificamente porque o `TokenRefreshSerializer` padrão do `simplejwt` deixa vazar `ObjectDoesNotExist` quando o usuário do claim foi apagado (ex.: banco restaurado) — isso virava HTML de erro 500 de ~128 KB para o cliente. A correção intercepta e devolve `401` (`no_active_account`).
- **Import duplicado de `JWTAuthentication`** em `app/account/views.py:14-15` — o import local do app é sombreado pelo do `simplejwt` (ver seção Regras de negócio acima). Reportado como inconsistência, não corrigido.
- **`GoogleAuthView`** trata separadamente falhas de validação de token (`ValueError`, logadas com `aud` do token vs. client id configurado para diagnosticar client id divergente) de falhas de rede/transporte (`503`, não `401`), evitando classificar problema de infraestrutura como token inválido.
- **Enumeração de e-mail evitada** em `PasswordResetRequestView` — resposta `200` genérica independentemente de o e-mail existir ou não.
- **`SupportConversation.session_key` e `summary`** estão definidos no modelo mas não são preenchidos por nenhuma view lida (`support_views.py`) — possivelmente campos legados ou reservados para uso futuro.
- **Signal `manage_client`, ramo de exclusão** depende de `kwargs.get('deleted', False)` vindo de fora do `post_save` padrão do Django — não foi possível confirmar no código lido quem emite esse kwarg; pode nunca ser exercitado na prática.
- **Emails com falha silenciosa:** praticamente todos os envios de e-mail no app (`credentials`, `support_ticket_confirmation`, `post_published`, criação de Jira issue) usam `try/except` amplo com `print`/`logger`, nunca interrompendo o fluxo principal — bom para robustez, mas significa que falhas de e-mail não ficam visíveis para o usuário nem para monitoramento automático além dos logs.
- **`UpdateUserView`** e **`UserMetaCreateView`/`UpdateUserMetaView`/`DeleteUserMetaView`** não declaram `permission_classes` próprias, então caem no `DEFAULT_PERMISSION_CLASSES` do projeto (`HasAPIKeyOrIsAuthenticated`) — qualquer usuário autenticado (não só admin/gestor) pode, em tese, atualizar qualquer `CustomUser` por `pk` ou criar/editar/apagar `UserMeta` de qualquer usuário, já que essas views não filtram por dono do recurso.
