## Responsabilidade

O app `app/conversation` guarda, num único lugar, as duas pontas da conversa de WhatsApp com o cliente: o que o ManyChat entrega (`inbound`, via webhook) e o que a Miggo envia (`outbound`, resposta manual da equipe ou automação de conteúdo). Além do histórico, o app é dono de um motor de flows com decisão (`engine.py`) que permite montar conversas ramificadas (ex.: "Aprovar" / "Pedir ajuste") sem depender de configurar cada ramo dentro do builder do ManyChat (`app/conversation/models.py:1-13`).

O ManyChat é sempre o canal de WhatsApp: ele dispara `sendFlow`/`sendContent` para falar com o cliente e chama nossos webhooks para entregar respostas e servir conteúdo dinâmico (Dynamic Block).

### ConversationFlowState — a máquina de estados da conversa (`app/conversation/models.py:296-331`)

Onde a conversa está dentro de um flow com decisão. **Só existe enquanto o fluxo está de pé**: some ao chegar num passo terminal ou ao expirar. Uma conversa participa de **um** flow por vez (`OneToOneField` com `Conversation`).

| Campo | Tipo | Obrigatório | Default/choices | Descrição |
|---|---|---|---|---|
| `conversation` | O2O → `Conversation` | Sim | `CASCADE`, `related_name='flow_state'` | Conversa dona (um estado por vez) |
| `flow` | FK → `MessageFlow` | Sim | `CASCADE`, `related_name='states'` | Flow em andamento |
| `step` | FK → `MessageFlowStep` | Não | `CASCADE`, `null=True` | Passo atual |
| `context` | JSONField | Não | `dict` | Respostas já dadas (`resposta.<passo>`) para interpolação nos passos seguintes |
| `started_at` | DateTimeField | — | auto | — |
| `updated_at` | DateTimeField | — | auto | — |
| `expires_at` | DateTimeField | Sim | indexado | Fim de vida do estado (24h — `engine.FLOW_STATE_TTL_HOURS`) |

**Propriedade**: `is_expired` (`models.py:328-331`) — `expires_at <= timezone.now()`.

<Note>
Não existe um campo `status`/enum de "estados possíveis" no sentido clássico de máquina de estados fixa — o estado real da conversa é **qual `MessageFlowStep`** o registro aponta (campo `step`), dentro de um grafo definido dinamicamente por `MessageFlow`/`MessageFlowStep`. Os "estados" possíveis, portanto, são os passos cadastrados de cada flow, mais dois estados implícitos: **sem estado** (nenhum `ConversationFlowState`, ou expirado — conversa fora de qualquer flow) e **terminal** (o registro é apagado assim que um passo sem `options` é alcançado e entregue). Veja a tabela de transições completa na seção [Engine](#o-motor-de-flows-engine-py) abaixo.
</Note>

**Onde `ConversationFlowState` é criado/alterado/apagado** (todas em `engine.py`):

| Operação | Função | Linha |
|---|---|---|
| Criar/atualizar (`update_or_create`) | `_save_state` | `engine.py:85-92` |
| Ler estado vivo (apaga se expirado) | `active_state` | `engine.py:65-78` |
| Apagar | `clear_state` | `engine.py:81-82` |
| Avançar `step`/`context`/`expires_at` (passo intermediário) | `resolve_reply` | `engine.py:301-305` |
| Apagar ao alcançar passo terminal | `resolve_reply` | `engine.py:299-300` |
| Apagar ao entregar a um flow do ManyChat (`flow_ns` na opção) | `resolve_reply` | `engine.py:283-286` |
| Apagar quando o `next_step` da opção não existe mais | `resolve_reply` | `engine.py:292-297` |
| Apagar após render de passo terminal no Dynamic Block | `webhooks.manychat_dynamic_block_continue` | `webhooks.py:161-164` |

**O que a view faz** (`services.handle_webhook`, `services.py:235-273`):
1. `upsert_conversation` — cria/atualiza a `Conversation` pelo `manychat_id`; na primeira vez, tenta resolver o `Client` via `resolve_client` (por `PlatformIntegration` de WhatsApp, depois e-mail, depois telefone).
2. Se não há texto nem mídia no payload (o ManyChat também usa esta URL só para sincronizar dados do subscriber), a thread é atualizada e a função retorna sem gravar mensagem.
3. Grava a `Message` (`direction='inbound'`, `source='manychat_webhook'`), atualiza `last_inbound_at` (reabre a janela de 24h) e incrementa `unread_count`.
4. Se havia texto, chama `engine.handle_reply` — se a conversa estiver no meio de um flow com decisão, a resposta é tratada como a escolha do cliente e o próximo passo é disparado. Erros do motor são capturados e logados (`except Exception`, `services.py:270-271`) para não derrubar o webhook.

**Resposta**: sempre `200` mesmo em erro interno de processamento (`{"detail": "processing error"}`) — propositalmente, para o ManyChat não reenviar a mesma mensagem em loop após um 5xx (`webhooks.py:66-68`). Em sucesso:

<ResponseField name="detail" type="string">`"ok"`</ResponseField>
<ResponseField name="conversation_id" type="integer" />
<ResponseField name="client_id" type="integer">Pode ser `null`</ResponseField>
<ResponseField name="message_id" type="integer">`null` se nenhuma mensagem foi gravada (payload só de sync)</ResponseField>

`400` se o payload não for objeto, ou se não der para extrair um `manychat_id`.
</Accordion>

<Accordion title="POST /webhooks/manychat/dynamic-block/continue/ — Dynamic Block">
URL fixa e única para todos os flows dinâmicos — é o único passo do "flow casca" configurado manualmente no builder do ManyChat (ver `engine.starter_flow_ns`) e também o destino de callback dos botões de decisão. Mesma verificação de token que `/webhooks/manychat/` (`webhooks.py:126-127`).

**Dois casos, pelo mesmo payload**, decididos pela presença de `option`:

<ParamField body="id" type="string">Id do subscriber — resolve a conversa via `services.conversation_for_block` (não sobrescreve `subscriber_data`, para não apagar `custom_fields` de envios seguintes)</ParamField>
<ParamField body="option" type="string">Ausente: o flow casca acabou de ser disparado por nós — só renderiza o passo já gravado no `ConversationFlowState`. Presente: o cliente tocou num botão — decide a ramificação nesta mesma resposta</ParamField>
<ParamField body="caption" type="string">Fallback de `option`</ParamField>
<ParamField body="custom_fields" type="object | array">Usado para atualizar o contexto de interpolação no momento da chamada — tem prioridade sobre o `subscriber_data` gravado</ParamField>

**Sem `option`** (disparo nosso, `webhooks.py:157-165`): lê `ConversationFlowState` da conversa; se não houver estado vivo, devolve bloco vazio. Monta o `content` do passo atual (`flows.build_step_content`, com `callback_url` apontando para esta mesma URL). Se o passo for terminal, apaga o `ConversationFlowState` **depois** de montar a resposta — só agora que o ManyChat de fato buscou o conteúdo.

**Com `option`** (toque num botão, `webhooks.py:167-228`):
1. Registra a escolha como mensagem `inbound` (`source='manychat_dynamic_block'`).
2. Chama `engine.resolve_reply` com o texto da opção.
3. Se a opção aponta para um `flow_ns` do ManyChat, dispara `sendFlow` e devolve bloco vazio (a conversa sai do fluxo dinâmico).
4. Se o próximo passo não existe mais (`next_step` apagado), devolve bloco vazio (o erro já foi logado por `resolve_reply`).
5. Se a resposta não casou com nenhuma opção (`matched=False`), reapresenta o passo atual com `fallback_text` (ou os blocos originais se não houver fallback configurado).
6. Se casou e há próximo passo: executa as ações do passo (`engine.render_step` → `run_actions`) e monta o `content` do próximo passo **na mesma resposta HTTP** — sem um novo `sendFlow`, porque o ManyChat já está esperando o conteúdo deste toque.

**Formato de resposta — Dynamic Block do ManyChat** (`flows.dynamic_block_response`, `flows.py:426-428`):

```json
{
  "version": "v2",
  "content": {
    "type": "whatsapp",
    "messages": [
      {"type": "text", "text": "Aprova o conteúdo desta semana?", "buttons": [
        {"type": "dynamic_block_callback", "caption": "Aprovar", "url": "<callback_url>", "method": "post", "payload": {"option": "Aprovar"}}
      ]}
    ],
    "actions": [],
    "quick_replies": []
  }
}
```

Quando não há nada a mostrar (estado ausente/expirado, passo só de ação, opção que entrega a um flow do ManyChat), a resposta é o bloco vazio de `_empty_dynamic_block` (`webhooks.py:84-85`):

```json
{"version": "v2", "content": {"type": "whatsapp", "messages": [], "actions": [], "quick_replies": []}}
```

Todo `content` devolvido carrega até 3 botões do tipo `dynamic_block_callback`, que fazem o ManyChat chamar esta mesma URL de volta com `option` preenchido (`flows._option_buttons`, `flows.py:341-361`) — e a mesma lista de opções sempre aparece também como texto numerado (`flows.options_text`), para o casamento funcionar mesmo em canais sem botão interativo.
</Accordion>

## Regras de negócio e funções

### O motor de flows (`engine.py`)

O motor existe porque **só um flow do ManyChat já em andamento consegue receber de volta o clique num botão**. `sendContent` avulso não tem como oferecer isso. Por isso toda entrega de um passo com decisão passa por um "flow casca": um único flow, criado manualmente uma vez no builder do ManyChat, com um passo de Solicitação Externa apontando para `/webhooks/manychat/dynamic-block/continue/`, cujo `flow_ns` fica na env var `DYNAMIC_FLOW_STARTER_FLOW_ID` (`engine.py:1-33`, `engine.starter_flow_ns`, `engine.py:49-58`). A ramificação em si (qual passo vem a seguir) acontece no nosso backend, nunca no ManyChat — porque quem decide depende de dado da plataforma (post, status, plano do cliente).

| Função | Assinatura | O que faz / decide |
|---|---|---|
| `starter_flow_ns()` | `() -> str \| None` | Lê `DYNAMIC_FLOW_STARTER_FLOW_ID` do ambiente (`engine.py:49-58`) |
| `active_state(conversation)` | `(Conversation) -> ConversationFlowState \| None` | Estado vivo da conversa; apaga e devolve `None` se expirado (`engine.py:65-78`) |
| `clear_state(conversation)` | `(Conversation) -> None` | Apaga o estado da conversa (`engine.py:81-82`) |
| `run_actions(conversation, step, context)` | `(...) -> (bool, str \| None)` | Executa os blocos `type='action'` do passo em ordem, via `actions.run`; grava cada resultado como `Message(source='system_action')`; a primeira falha interrompe (ações são pré-condição da mensagem) (`engine.py:95-133`) |
| `render_step(conversation, flow, step, context)` | `(...) -> (content \| None, preview, ok, erro)` | Roda as ações do passo e monta o `content`/preview, sem falar com o ManyChat; `content is None` com `ok=True` é um passo só de ação (`engine.py:136-159`) |
| `send_step(conversation, flow, step, *, sent_by=None, context_extra=None)` | `(...) -> (Message \| None, erro \| None)` | Grava o `ConversationFlowState` **antes** de acionar o ManyChat, dispara `sendFlow` para o flow casca e registra a `Message` (`source='manychat_dynamic_flow'`) — o conteúdo já é conhecido aqui, só a entrega passa pelo Dynamic Block (`engine.py:162-209`) |
| `start(conversation, flow, *, sent_by=None, context_extra=None)` | `(...) -> (Message \| None, erro \| None)` | Envia o passo de entrada do flow (`flow.entry_step`) via `send_step` (`engine.py:212-222`) |
| `_send_fallback(conversation, state)` | `(...) -> Message \| None` | Reapresenta o passo atual com `fallback_text` quando a resposta não casou (`engine.py:225-249`) |
| `resolve_reply(conversation, text)` | `(...) -> dict` | **Decide** para onde a resposta leva, sem enviar nada — usado tanto no webhook de texto quanto no toque de botão do Dynamic Block (`engine.py:252-308`) |
| `handle_reply(conversation, text)` | `(...) -> (state \| None, Message \| None)` | Caminho do webhook de texto: resolve e **dispara** o próximo passo via `send_step` (`engine.py:311-347`) |

`resolve_reply` casa o texto contra `state.step.options` (via `flows.match_option`) e devolve um dicionário `{matched, step, flow_ns, context, state}`:
- Sem estado vivo ou sem opção casada → `matched=False`.
- Opção com `flow_ns` preenchido → apaga o estado, devolve `flow_ns` (a conversa sai do fluxo dinâmico e passa a ser tocada por um flow puro do ManyChat).
- Opção com `next_step` que não existe mais (passo apagado após o flow ter começado) → loga erro e apaga o estado.
- Opção com `next_step` terminal → apaga o estado.
- Opção com `next_step` não terminal → atualiza `step`/`context`/`expires_at` do estado existente.

#### Máquina de estados do fluxo — estados e transições

"Estado" aqui é `ConversationFlowState.step` (ou a ausência do registro). Transições reais implementadas:

| Estado atual | Evento | Próximo estado | Onde |
|---|---|---|---|
| sem estado | equipe dispara `dispatch_flow`/`send_dynamic_flow` (`kind='dynamic'`) | `step = flow.entry_step` | `engine.start` → `send_step` → `_save_state` (`engine.py:187`, `engine.py:212-222`) |
| passo X (não terminal) | cliente responde texto que casa com uma opção com `next_step=Y` (Y não terminal) | `step = Y` | `resolve_reply` (`engine.py:301-305`), disparado por `handle_reply` → `send_step` |
| passo X (não terminal) | cliente responde texto que casa com opção com `next_step=Y` terminal | estado apagado (Y é entregue e a conversa encerra o fluxo) | `resolve_reply` (`engine.py:299-300`) + `send_step` entrega Y |
| passo X | cliente responde texto que casa com opção com `flow_ns` preenchido | estado apagado; `sendFlow` do `flow_ns` disparado | `resolve_reply` (`engine.py:283-286`) + `handle_reply` (`engine.py:332-337`) |
| passo X | cliente responde texto que casa com opção cujo `next_step` foi apagado do banco | estado apagado, erro logado | `resolve_reply` (`engine.py:288-297`) |
| passo X | cliente responde texto que **não** casa com nenhuma opção | estado inalterado; fallback reenviado | `handle_reply` → `_send_fallback` (`engine.py:225-249`, `engine.py:329-330`) |
| passo X | `expires_at` vencido (24h sem interação) | estado apagado na próxima leitura | `active_state` (`engine.py:73-78`) |
| passo X (toque em botão, via Dynamic Block) | mesma lógica de `resolve_reply`, mas a entrega do próximo passo acontece **na mesma resposta HTTP**, sem novo `sendFlow` | idem acima | `webhooks.manychat_dynamic_block_continue` (`webhooks.py:167-228`) |
| passo terminal já entregue (disparo nosso, sem `option`) | ManyChat chama `/dynamic-block/continue/` para buscar o conteúdo | estado apagado (só depois da resposta montada) | `webhooks.py:161-164` |

#### O Dynamic Block: onde é montado

A view `manychat_dynamic_block_continue` (`webhooks.py:88-228`) é o único ponto que monta a resposta final do Dynamic Block. Ela usa:
- `flows.build_step_content` / `flows.build_content` para montar `content.messages` a partir dos blocos do passo (`flows.py:386-424`).
- `flows.dynamic_block_response` para envelopar em `{"version": "v2", "content": {...}}` (`flows.py:426-428`).
- `flows._option_buttons` para transformar as `options` do passo em botões `dynamic_block_callback` apontando de volta para a mesma URL, limitados a 3 (`flows.py:341-361`).
- `_empty_dynamic_block` (`webhooks.py:84-85`) quando não há nada a mostrar.

## Erros comuns / pontos de atenção

<Warning>
`sendContent` (`/send/` manual e flows `kind='dynamic'`) só funciona dentro da janela de 24h desde a última mensagem do cliente (`Conversation.is_window_open`). Fora dela, o endpoint responde `409` e nada é enviado. Já `sendFlow` (flows `kind='manychat'`, automações) não tem essa restrição.
</Warning>

<Warning>
Flow dinâmico com decisão (`kind='dynamic'` com `options`) exige `DYNAMIC_FLOW_STARTER_FLOW_ID` configurado — sem o flow casca criado manualmente no builder do ManyChat, `send_step` recusa o envio com a mensagem "Flow casca do Dynamic Block não configurado..." (`engine.py:192-199`) e `MessageFlow.is_available`/`starter_configured` já sinalizam isso no construtor antes do disparo.
</Warning>

<Warning>
O ManyChat responde `200`/`201` mesmo quando o envio falha — o veredito real está no corpo (`status: "success"`). Qualquer integração nova com a API do ManyChat precisa checar isso, não só o status HTTP (`services.py:320-321`, `services.py:383-384`).
</Warning>

<Warning>
Apagar um passo (`MessageFlowStep`) referenciado por `next_step` de uma opção de **outro** flow que já tem conversas em andamento não é bloqueado pela validação de escrita (`_validate_grafo` só valida dentro do mesmo flow ao salvar) — se isso acontecer, `resolve_reply` encerra o fluxo da conversa e loga erro (`engine.py:288-297`), mas o cliente fica sem resposta.
</Warning>

<Warning>
Os dois webhooks (`/webhooks/manychat/` e `/webhooks/manychat/dynamic-block/continue/`) sempre respondem `200`/`503`/`401` — nunca `500` em erro de processamento do payload — de propósito, para o ManyChat não reenviar a mesma requisição em loop. Isso significa que um erro real de processamento fica visível só nos logs, não no código HTTP.
</Warning>

<Warning>
`MessageFlow.delete()` via API (`DELETE /flows/<id>/`) na verdade desativa (`is_active=False`), nunca apaga o registro — o dado no banco persiste indefinidamente.
</Warning>

<Note>
Não há endpoint de "excluir mensagem" nem de edição de mensagem já enviada — o histórico é append-only pelo desenho do módulo.
</Note>
