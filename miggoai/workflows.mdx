Os workflows vivem em `backend/apps/generations/services/`. Cada um é uma chave de `Workflow` no CMS de prompts:

| Chave | Gera | Módulo |
|---|---|---|
| `title` | título (microângulos) ou cards do carrossel | `title_workflow.py` |
| `image` | imagem do post | `image_workflow.py` |
| `caption` | legenda | `caption_workflow.py` |
| `hashtags` | hashtags | `hashtags_workflow.py` |
| `grid` | mosaico 3x3 do onboarding | `grid_workflow.py` |
| `bio` | bio de perfil (Instagram ou LinkedIn) | `bio_workflow.py` |
| `banner` | banner de capa do LinkedIn (arte de IA + composição em HTML) | `banner_workflow.py` + `composicao.py` |
| `destaques` | capas de destaque do Instagram (template HTML, sem IA) | `destaques_workflow.py` + `composicao.py` |
| `estrategia` | um item da estratégia inicial por geração (bio, destaques, Sobre e banner) | `estrategia_workflow.py` |
| `briefing` | briefing preenchido a partir de uma fonte (Instagram, site, dedução ou documento) | `briefing_workflow.py` |
| `pauta` | ideia do cliente formatada em pauta | `pauta_workflow.py` |
| `diagramacao` | diagramação de uma referência de design, e quadros e posts de um grid de cliente | `diagramacao_workflow.py` |

## Núcleo

### `runner.py` — ponto único de execução

#### `run_workflow(workflow_key, client_id, post_id, environment, user, variable_overrides=None) -> Generation`

`backend/apps/generations/services/runner.py`.

**Parâmetros**:
- `workflow_key` (`str`) — uma das chaves da tabela acima.
- `client_id` / `post_id` (`int`) — ids no backend-miggo (`post_id` é `None` nas peças de perfil e no grid).
- `environment` (`str`) — `Generation.ENV_TEST` ou `Generation.ENV_PRODUCTION`.
- `user` — usuário Django autenticado (ou `None`/anônimo).
- `variable_overrides` (`dict`, opcional) — valores que sobrescrevem o contexto automático.

**Passo a passo**:
1. Cria a `Generation` já como `RUNNING` (precisa do `id` para o path das imagens).
2. Se `variable_overrides` tem `format_key` sem `formato_motivo`, injeta `formato_motivo = 'escolhido manualmente na geração'`.
3. Salva os overrides "persistíveis" (exclui chaves de encadeamento e voláteis) em `ClientVariableValue`, via `client_services.save_variables`. Com `salvar_variaveis=False` (o painel de IA no `/admin` da Plataforma) esse passo é pulado: o override vale só para a execução, e gravar o padrão do cliente vira ação explícita (`PUT /api/clients/<id>/variables/`).
4. Monta o contexto com `context_builder.build_context(client_id, post_id)`.
5. Sobrepõe respostas já salvas do cliente (exceto voláteis) por cima do contexto fresco.
6. Despacha para o runner do workflow certo (`_WORKFLOW_RUNNERS[workflow_key]`), passando `context`, `variable_overrides` e um callback `on_stage` que atualiza `Generation.stage` em tempo real (salva imediatamente, não espera o fim — para o polling do painel).
7. Se o resultado trouxer `images` (lista de `PIL.Image`), salva cada uma em `MEDIA_ROOT/generations/{test|production}/<generation_id>/imagem[_cardN].png` e preenche `image_paths`.
8. Fecha a `Generation` como `SUCCESS` ou `FAILED` — **sempre**, mesmo se o workflow levantar exceção (`try/except/finally`, nunca deixa a exceção subir sem salvar o estado).

**Efeitos colaterais**: grava em `ClientVariableValue`, cria arquivos PNG em `MEDIA_ROOT`, chama a API da OpenAI (rede), grava `Generation` no banco a cada mudança de estágio.

**Erros possíveis**: qualquer exceção do workflow (`RuntimeError` de prompt ausente, erro de rede da OpenAI, `PromptDefinition.DoesNotExist`) é capturada e vira `Generation.status = FAILED` com `error = str(exc)` — nunca propaga ao chamador HTTP como 500 (a view devolve 502 com o objeto serializado).

#### `run_complete(client_id, post_id, environment, user, variable_overrides=None) -> list[Generation]`

Roda os 4 workflows em sequência, encadeando a saída de um no próximo; cada passo vira sua própria `Generation`, agrupada numa `Execucao`.

1. Roda `title` — se falhar, devolve `[title_gen]` e para.
2. Extrai `angle`, `texto_imagem` (lista para carrossel, string para os demais) e o `format_key`/`formato_motivo` sorteados no título.
3. Roda `image` com `{texto_imagem, titulo_selecionado: angle, format_key, formato_motivo}` — sempre executado, mesmo se falhar, a lista continua.
4. Roda `caption` com o mesmo `angle`/`format_key`.
5. Se `caption` teve sucesso e não foi `skipped`, roda `hashtags` com `legenda_post` = a legenda gerada.

Devolve sempre a lista de `Generation`s já criadas (1 a 4 itens), mesmo em falha parcial.

### `context_builder.py` — montagem do contexto

#### `build_context(client_id: int, post_id: int) -> dict`

`backend/apps/generations/services/context_builder.py`. Busca dados ao vivo no backend-miggo e monta o dict usado para renderizar os prompts.

Passos internos:
1. `clients_services.get_client_detail` + `get_briefing`.
2. `_listar_historico` — histórico de posts `published`/`approved`/`sent` na janela `hoje-60d` até `hoje+365d` (`HISTORICO_MAX_DIAS = 60`). Cacheado por dia em `ClientPostHistory` — só consulta o backend-miggo uma vez por cliente por dia; se a consulta falhar e já existir um retrato de dia anterior, usa-o como fallback com log de warning; sem nenhum retrato salvo, propaga o erro e a geração falha.
3. `posts_services.get_post_detail(post_id)`.
4. `clients_services.get_client_grid` — grid 3x3 do brandkit.
5. `_escolher_formato(post_detail)` — resolve `format_key` (`story`/`feed`/`carrossel`/`reel`): usa o `post_format` explícito do card se houver; senão sorteia entre `suggested_formats`; sem nenhum dos dois, cai em `story`.

**Retorna** (chaves principais): `client_id`, `cliente_nome`, `briefing_texto`, `negocio`, `diferenciais`, `publico_alvo`, `posts_recentes` (texto formatado), `calendario_assunto`, `calendario_objetivo`, `calendario_macro_objetivo`, `calendario_tags`, `calendario_cta`, `cta_required`, `grid_url`, `instagram_handle`, `post_format`, `format_key`, `formato_motivo`, e `_raw` (dict com os objetos brutos — removido antes de expor via API).

**Briefing por seções.** Só os campos listados em `_BRIEFING_SECOES` entram no `briefing_texto`; campos técnicos/de integração do client-meta (EAV) nunca vazam para o prompt. `_formatar_briefing` monta blocos rotulados, na ordem de prioridade da copy:

| Seção | Campos do client-meta |
|---|---|
| `NEGÓCIO` | `company`, `business`, `sub_business`, `region`, `target`, `ticket`, `summary`, `services`, `instagram`, `site`, `linkedin`, `linkedin_profile_type` |
| `PÚBLICO E DORES` | `audience_profile`, `audience_pain`, `audience_goals` |
| `DIFERENCIAIS` | `differential` (em lista: um item por linha ou separado por `;`) |
| `TOM DE VOZ` | `tone_of_voice` |
| `CTAS DO CLIENTE` | `ctas` (em lista) |
| `OBJETIVOS` | `goals` |
| `IDENTIDADE VISUAL` | `visual_style`, `typography`, `visual_references` |
| `OUTRAS INFORMAÇÕES` | `brand_knowledge` (rótulo "Materiais da marca"), `extra`, `referer` |

- Dados pessoais (`fullname`, `email`, `nickname`) não entram no prompt.
- `brand_knowledge` e `extra` vão numa linha só (quebra de linha não forja campo novo); `extra` é truncado em `BRIEFING_EXTRA_MAX_CARACTERES = 600`.
- `calendario_cta` vazio vira `CTA_PADRAO` ("a ação dos CTAs do briefing"), para o prompt não montar "direcionada ao ,".

### `output_contract.py` — contrato de saída fixo

Ver detalhes em [Prompts](/miggoai/prompts). Define 4 contratos (`TITULO_TEXTO`, `TITULO_CARDS`, `LEGENDA`, `HASHTAGS`), cada um com um `schema` JSON (`json_schema`, `strict: True`) e uma `instruction` textual anexada ao prompt renderizado. `apply(key, rendered_prompt) -> (prompt_final, schema)`.

### `title_workflow.run(context, variable_overrides=None, on_stage=None) -> dict`

`backend/apps/generations/services/title_workflow.py`.

1. Resolve `format_key` (de `variable_overrides` ou `context`) e o `slug` do prompt (`titulo-story`/`titulo-feed`/`titulo-carrossel`).
2. Busca o `PromptDefinition` ativo, renderiza com `context + variable_overrides`, aplica o contrato de saída.
3. Chama `openai_service.chat_json` (structured output).
4. `_extrair_microangles` — normaliza a resposta.
5. Para carrossel, corta cards acima de `CARDS_MAX = 8` (`_limitar_cards`) — teto reforçado no código porque `strict: True` não aceita `maxItems` no schema.
6. Se não for carrossel, chama `_select_best_microangle` — um **agente interno** com prompt fixo (não editável no CMS) que escolhe o melhor dos 3 microângulos gerados.

Dois blocos do sistema são acrescentados ao prompt do CMS quando se aplicam:

- **CTA no story** (`_bloco_cta_do_story`): story não tem legenda; com `cta_required`, o texto da arte fecha com o CTA do calendário.
- **Estrutura do texto na arte** (`_linha_visual_do_post`): em feed e story, a referência de design que a arte vai seguir é escolhida já aqui. Se ela vai à geração como wireframe, o prompt recebe os blocos de texto da peça, na ordem de leitura, com o papel de cada um e quantos caracteres cabem, para o texto nascer do tamanho deles. A chave da referência sai no resultado (`linha_visual`) e é encadeada para a imagem, que não sorteia outra. Carrossel não recebe o bloco.

**Retorna**: `{prompt_slug, prompt_version_used, format_key, formato_motivo, microangles, selected_microangle, selection_reason, selection_score}`, mais `linha_visual` quando a referência foi escolhida no título.

O schema de cards traz `direcao_visual` por card (usada no prompt da imagem) e o resultado passa adiante o nome do formato e a referência de copy usados, que a imagem e a legenda herdam (`runner._referencia_do_titulo`). O texto passa pela guarda `texto_limpo` (ver abaixo).

**Erros**: `RuntimeError` se a OpenAI devolver erro ou nenhum microângulo.

### `image_workflow.run(context, variable_overrides=None, on_stage=None) -> dict`

`backend/apps/generations/services/image_workflow.py`. Não encadeia com o título por si só — recebe `texto_imagem` via `variable_overrides` (o chamador decide).

1. Resolve tamanho (`IMAGE_FORMAT_SIZES`/`IMAGE_GEN_SIZES` de `openai_service`) pelo `format_key`.
2. Exige `texto_imagem` (`str` ou `list[str]`, 1 item por card no carrossel) — `RuntimeError` se ausente.
3. **Predefinição `usage` do cliente** (`usar_midia_cliente = bool(media_id_forcado) or _deve_consultar_galeria(usage)`) decide se a galeria é **consultada** nesta geração: `always` sim, `never` não, `alternate` sorteio 50/50 (não qual foto — isso é decidido depois).
4. Se consultada: busca `get_client_media_library`, e por card roda `media_matcher.rankear` (peneira léxica) seguido de `media_classifier.selecionar` (julgamento por IA da descrição). Toda a trilha de decisão (candidatos, score, motivo) é registrada em `midia_cliente` no resultado, para auditoria. Com `always` e todas as fotos dentro da janela de reuso, a escolha volta às usadas há mais tempo, uma por card (`reuso_relaxado`).
   - **Banco de imagens da Miggo**: se a preferência do cliente tem `use_stock=True`, o pool do banco é **unido ao da galeria** e segue o mesmo funil — `_deve_consultar_banco` é irmã de `_deve_consultar_galeria` e roda depois dela, então o banco só entra quando esta geração já ia usar foto real. Detalhe em [Banco de imagens no funil](#banco-de-imagens-no-funil).
5. `_resolver_marca` decide logo/assinatura: por padrão consulta a preferência salva no backend-miggo (`get_signature_preference`); `variable_overrides` com `marca_modo`/`assinatura_tipo`/`assinatura_texto` sobrescrevem pontualmente sem persistir.
6. Escolhe a referência de design do post (ver [Referência de design](#referência-de-design-wireframe-e-formato)) e, para cada texto (1 por card), renderiza o prompt `imagem-post` com os blocos do sistema: papel de cada imagem enviada, especificação do wireframe, estilo da peça e paleta da marca.
7. Gera a imagem (`_gerar`): com alguma imagem de entrada, `openai_service.generate_image` (`images/edits`); sem nenhuma, `openai_service.gerar_arte` (`images/generations`). Nos dois casos em qualidade `high` (`QUALIDADE_IMAGEM_POST`).
8. Confere a arte no [guard](#guard-da-arte) e redimensiona (`redimensionar_para_entrega`) — normalmente um no-op porque o tamanho pedido já é o tamanho final.

**Retorna**: `{prompt_slug: 'imagem-post', prompt_version_used, format_key, formato_motivo, width, height, rendered_prompts, midia_cliente, variacao, guard, images}` — `images` é uma lista de objetos `PIL.Image` (o `runner` salva em disco).

**Imagens enviadas ao modelo** (`_ordenar_imagens`), nesta ordem: o guia de diagramação (wireframe ou esqueleto), a foto do cliente ou do banco, o logo. A primeira da lista é `images[0]`. **O grid do cliente não vai à geração de imagem.**

- **Paleta** (`_bloco_da_paleta`): os hex do brandkit entram como regra do sistema; branco e preto são liberados para contraste e as cores da foto do cliente ficam como estão. Cliente sem paleta segue sem o bloco.
- **Foto real** (`PAPEL_DA_FOTO`): a foto do cliente ou do banco entra literal na peça, sem redesenhar pessoa nem produto. Peça pronta (arquivo `template_*` ou descrição que abre com "Post") não vale como foto real (`media_matcher.e_peca_pronta`).
- **Tela do produto** (`PAPEL_DA_TELA_DO_PRODUTO`): quando a foto escolhida para o card tem `image_type: tela_do_produto` na análise da galeria, ela entra inteira dentro de um aparelho, sem recorte nem recoloração, e o texto do card fica fora dele. A regra é da foto escolhida, não do cliente.
- **Carrossel não repete foto** entre os cards da mesma geração: as fotos já usadas saem do pool dos cards seguintes.
- **Referências conferidas antes da chamada** (`openai_service.referencia_acessivel`): arquivo ausente (404) não é enviado; linha visual com slide ausente é trocada pela próxima. Endereço local/privado que a OpenAI não alcança é baixado e enviado como data URL (só em `DEBUG`; em produção é recusado), com validação de IP a cada redirect e teto de 12 MB.
- **Erro para a tela é frase nossa** (referência, filtro de segurança ou genérica); o corpo da OpenAI fica só no log.

#### Referência de design: wireframe e formato

A referência de design (`DesignReference` tipo `post`, do backend-miggo) é escolhida pelo código (`services/variacao_visual.py`), não pelo modelo.

- **Só entra no sorteio a referência com diagramação aprovada** (`diagramacao.liberada`: `estado` `aprovado`, pelo juiz ou pela equipe). A referência com dono (`client`) só vale para o cliente dono.
- **Mesmo formato do post, sem exceção** (`_do_formato`): carrossel usa carrossel de referência (slides do mesmo `par_id`, um por card); story e reel usam peça em pé; feed usa peça de feed. Sem referência do formato, a peça sai sem referência de design. A regra vale também para o link da referência de copy e para a linha escolhida no título.
- **Sorteio** entre as `TOP_REFERENCIAS = 5` mais afins à pauta, fora da janela de reuso (`JANELA_DIAS = 30`), com a mesma chance entre referências genéricas e as extraídas do grid do cliente, e alternando o tom do fundo em relação ao último post.
- **Wireframe** (`services/diagramacao.py`): a referência vai ao modelo como o wireframe desenhado pela Plataforma (`wireframe_url`, ou `wireframe_sem_corpo_url` no card sem corpo), acompanhado da especificação: camadas de trás para frente, posição em % da peça, linhas e altura da letra de cada bloco de texto, quem fica na frente de quem e o estilo visual da peça. Os itens vão com nome neutro (`texto 1`, `objeto 1`): o nome original descreve a referência e traria o conteúdo dela para a arte.
- **Texto pelos blocos** (`trechos_do_card`): no card de um texto só, o texto é dividido pelos blocos da referência. Quem divide é o modelo de texto do workflow `diagramacao`, pelo sentido; o código confere que os trechos, emendados, devolvem o texto palavra por palavra. Sem divisão exata, vale o corte mecânico pela capacidade de cada bloco. A decisão fica no nó `divisao-do-texto`.
- **Esqueleto** (`referencia_estrutural.py`): quando o arquivo do wireframe está fora do ar, a referência vai como esqueleto em blocos cinza, sem cores nem rosto.
- **Teste do painel:** `referencia_design_id` em `variable_overrides` força uma referência, mesmo reprovada. É o que o painel de IA usa para testar uma referência antes de aprová-la.

O motivo de cada escolha vai para a auditoria (nós "Referência de copy", "Variação visual" e "Imagem").

#### Guard da arte

`services/guard_da_arte.py`. Depois de gerada, toda arte passa por uma chamada de visão (prompt `diagramacao-guard-da-arte` e modelo de texto do workflow `diagramacao`). O guard recebe a arte inteira, o guia de diagramação quando houve, e a arte em recortes na resolução gerada.

| Defeito | O que é |
|---|---|
| `bloco_do_guia` | barra, elipse ou forma vazia desenhada no lugar de um bloco do guia |
| `figura_pixelada` | pessoa ou área em pixels grandes, mosaico ou tarja |
| `artefato_de_geracao` | sopa de pixels, letra de contorno tremido ou ilegível, logo ou mão deformados |

Com defeito, a arte é refeita com o defeito descrito no prompt, até `MAX_REGERACOES = 2` vezes; esgotado, a última tentativa é entregue. O resultado vai em `guard.por_card` (`aprovada`: `true`, `false` ou `null` para "não conferida") e no nó `guard` da auditoria. O guard nunca derruba a geração: sem o prompt no CMS ou com a IA fora, a arte segue como não conferida.

**Efeitos colaterais**: chamadas de rede à OpenAI (`images/edits`, timeout 300s por card); nenhuma escrita em disco dentro do próprio workflow (feita pelo `runner`).

### `caption_workflow.run(context, variable_overrides=None, on_stage=None) -> dict`

`backend/apps/generations/services/caption_workflow.py`.

- **Guard**: se `format_key in {'story'}`, devolve `{'skipped': True, 'reason': 'Stories não usam legenda (formato efêmero).'}` sem chamar IA.
- Caso contrário, busca `PromptDefinition` `legenda-post`, monta `legendas_recentes` (até 10 legendas do histórico) e `cta_guard` (obrigatório vs. opcional, conforme `cta_required`/`calendario_cta`), renderiza e chama `openai_service.chat_json` com o contrato `LEGENDA`.

**Tese do post:** o prompt renderizado ganha o bloco `TESE DO POST` com o texto inteiro do título escolhido (não só o rótulo do ângulo). No carrossel, avisa que o último card já fecha com CTA, para a legenda não pedir uma segunda ação diferente. O CTA do calendário só é exigido quando não é o `CTA_PADRAO`.

**Retorna**: `{prompt_slug: 'legenda-post', prompt_version_used, format_key, caption, cta_used, reason}` (ou o dict `skipped`).

**Erros**: `RuntimeError` se a OpenAI devolver erro.

### `hashtags_workflow.run(context, variable_overrides=None, on_stage=None) -> dict`

`backend/apps/generations/services/hashtags_workflow.py`. Mesma estrutura do de legenda:

- **Guard**: `format_key in {'story'}` → `{'skipped': True, 'reason': 'Stories não usam hashtags (formato efêmero).'}`.
- Monta `hashtags_recentes` (até 30 hashtags únicas dos últimos 10 posts do histórico), renderiza `hashtags-post`, chama a OpenAI com o contrato `HASHTAGS`.

**Retorna**: `{prompt_slug: 'hashtags-post', prompt_version_used, format_key, hashtags, reason}` (ou `skipped`).

### `texto_limpo.py` — guarda contra marcas de texto de IA

Roda **depois** da geração, no título, no texto da arte, na direção visual e na legenda, então vale para qualquer prompt editado no CMS. `limpar` troca travessão (`—`/`–`) por vírgula, por hífen em intervalo numérico e por nada no início de linha; `limpar_estrutura` aplica em dicts/listas aninhados. Vocabulário de IA não é trocado por regra: fica na instrução do contrato (`output_contract.PROIBIDO_DE_IA`), anexada aos prompts de título, cards e legenda.

### `grid_workflow.py` — identidade do cliente no mosaico

A referência de estilo do grid é o mosaico de outra marca (ou um template com placeholder), e o prompt manda recriá-la célula a célula. `_bloco_identidade(marca_nome, marca_arroba)` entra nos dois modos (re-skin e correção): passa o nome e o @ reais do cliente e proíbe reproduzir nome de marca, @perfil, logo, site, telefone, assinatura ou placeholder ("@suamarcaaqui") da referência. Sem nome informado, a instrução é não escrever marca nenhuma.

### Peças de perfil: bio, banner e destaques

- **Bio** (`bio_workflow.py`): texto, com formato e teto de caracteres definidos pela Plataforma no pedido (`rede`, `max_caracteres`).
- Sem cor ou briefing no pedido (geração pelo painel), banner e destaques usam a paleta do brandkit e o briefing do cliente; `paleta=[]` vinda do onboarding é respeitada.
- **Banner do LinkedIn** (`banner_workflow.py`): a IA gera só a arte de fundo, quadrada, por `openai_service.gerar_arte` (`images/generations`, modelo de imagem da config do workflow); a peça final é composta em HTML e renderizada pelo Chromium do Playwright (`composicao.py`). O banner não leva logo. A arte de fundo é guardada (`result.banner.arte_path`) e reaproveitada no ajuste seguinte quando o pedido não fala da arte.
- **Capas de destaque** (`destaques_workflow.py`): sem IA. Template HTML determinístico (cúpula, ícone e legenda), renderizado pelo Chromium, para as capas saírem iguais entre si.

### `diagramacao_workflow.py` — diagramação da referência e grid do cliente

Chamado só pela Plataforma, em `POST /api/generations/referencia/diagramacao/` (síncrono). O cliente é opcional: referência global não tem dono.

**Referência de post** (padrão). Até três rodadas, no máximo seis chamadas de visão:

1. **Extração** (`diagramacao-extracao`): a referência vai com uma grade de 10 em 10% e o modelo devolve os itens (tipo, camada, caixa em %, papel do texto) e o estilo da peça (linguagem, tratamento da foto, textura, formas).
2. **Juiz** (`diagramacao-juiz`): confere item a item, vendo um recorte por item com a caixa contornada.
3. **Correção** (`diagramacao-correcao`): só dos itens reprovados; os aprovados ficam travados.

No fim (`_fechar`), forma gráfica menor que 0,5% da peça sai do body e são escolhidos os `blocos_do_texto`: o título e os maiores blocos de texto, até três, sem microtexto, na ordem de leitura. O body volta com `estado` `aprovado` ou `reprovado`. Sem bloco de título a geração falha (`DiagramacaoInvalida`) e a rota responde `502`.

**Grid de cliente** (`"tipo": "grid"`). Uma chamada de visão (`diagramacao-quadros-do-grid`) mede a caixa de cada post do mosaico, sem supor 3x3, e cada quadro é recortado e recriado em alta qualidade pelo modelo de imagem (`diagramacao-recriar-quadro`), no tamanho mais próximo da proporção dele (9:16, 4:5 ou 1:1). A resposta traz `quadros`, cada um com a caixa, `imagem_url` e `recriada`; quando a geração de um post falha, ele segue com o recorte. O grid com os quadros numerados e as peças ficam salvos na geração.

### Estratégia inicial, briefing e pauta

Workflows de perfil chamados pela Plataforma, com o schema de saída no próprio módulo.

- **`estrategia`** (`perfil/strategy/`): um item por geração (`ig-bio`, `ig-highlights`, `li-overview`, `li-banner`). Item fora da régua (bio até 150 caracteres, Sobre do LinkedIn entre 1.000 e 2.000, 6 destaques) ou falha transitória da OpenAI vira `EstrategiaReprovada`, e o worker repete.
- **`briefing`** (`perfil/briefing/`): uma fonte por chamada (`instagram`, `site`, `deducao`, `documento`). O conteúdo coletado entra delimitado e marcado como dado; a coleta continua na Plataforma. O schema da resposta é montado pelos tipos dos campos pedidos (`texto`, `lista`, `cores`).
- **`pauta`** (`perfil/pauta/`, sempre síncrono): a ideia do cliente (título e descrição) vira `{titulo, tema, formato_id, cta}`. O texto do cliente entra delimitado e o `formato_id` só é aceito entre os ids recebidos.

Com fila ativa e `idempotency_key`, `perfil/strategy/` e `perfil/briefing/` respondem `202` e o resultado sai por `perfil/by-key/`; sem fila são síncronos e respondem `502` na falha.

### Banco de imagens no funil

A foto do banco entra no **mesmo ponto** do pipeline que a foto de galeria — é isso que garante, por construção, que layout, paleta e tipografia da marca não mudem por causa da origem da imagem.

- **Quando entra**: `_deve_consultar_banco(usar_midia_cliente, client_id, use_stock, media_id_forcado)` — exige que a geração já fosse usar foto real, que o cliente tenha `use_stock=True` e que não haja `media_id` forçado.
- **De onde vem**: `clients_services.get_acervo_elegiveis(client_id)` chama `GET media/acervo/elegiveis/?client_id=&fadiga=1` no backend-miggo com o header `Acervo-Service-Token` — **nunca** a `MIGGO_API_KEY`, que aquelas rotas recusam. A anti-fadiga do banco é server-side (a janela é o `reuse_days` do cliente); a da galeria continua sendo a local (`_media_usadas_recentemente`).
- **Como se mistura**: `_adaptar_foto_do_banco` traduz a foto do acervo para o **formato da galeria**, em vez de cada etapa ganhar um ramo "se for do banco"; a origem fica em `_fonte` (`galeria`/`banco`) e o id no pool unido é o id real **negativo**, porque as duas sequências começam em 1. O `rankear` → `selecionar` segue igual.
- **Registro de uso**: quando a peça sai com foto do banco, o `runner` chama `registrar_usos_do_banco`, que faz `POST media/acervo/uso/`. Fica no `runner`: só registra depois das imagens salvas. A falha desse POST é logada e **não derruba** a geração.
- **Sem `ACERVO_SERVICE_TOKEN` o banco é simplesmente ignorado**, com `WARNING` no log: a ausência da credencial não pode virar "o banco está vazio" em silêncio, que é indistinguível de cliente sem foto elegível.

A trilha fica em `midia_cliente` no resultado (inclui `banco_habilitado` e a fonte usada), que é o que o admin lê para auditar a escolha.

### `media_matcher.py` — peneira léxica da galeria

Sem chamada de rede/IA — comparação local com `difflib` (stdlib).

- `rankear(texto_busca, media_items, threshold=0.35, limite=None) -> [(item, score), ...]` — só itens elegíveis (`_elegivel`: passaram pela análise do backend `analyze_media_library` E não foram marcados como impróprios para referência), ordenados por score decrescente.
- `_score(a, b)` — máximo entre containment (quanto do texto do post aparece na descrição), Jaccard e `SequenceMatcher.ratio()`.
- `find_best_match(texto_busca, media_items, threshold=0.35)` — atalho para o item top-1.

### `media_classifier.py` — julgamento por IA

- `selecionar(pauta, candidatos, model='gpt-4o-mini') -> {'item', 'media_id', 'motivo'}` — envia até `MAX_CANDIDATOS = 5` candidatos (já peneirados pelo `media_matcher`) num prompt fixo pedindo `{"media_id": <id ou null>, "motivo": "..."}`. Qualquer falha (rede, JSON inválido, id inventado/alucinado) resulta em **nenhuma foto** — a geração segue sem foto do cliente, que é considerado o comportamento correto (usar foto é exceção, não caminho crítico).
