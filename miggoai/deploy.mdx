O `miggoai_v2` gera **duas imagens** a partir da raiz do repositório: `Dockerfile.backend` (Django + Gunicorn) e `Dockerfile.frontend` (React servido pelo Nginx). Não há `docker-compose.yml` versionado: os serviços são configurados no Dokploy.

## Build das imagens no ECR (GitHub Actions)

O workflow `.github/workflows/docker-ecr.yml` (MIG-494) constrói as duas imagens e as publica no **Amazon ECR**. Ele **não faz deploy**: a troca de versão no Dokploy continua manual.

| Item | Como está no workflow |
| --- | --- |
| Gatilho | `push` na `main` e `workflow_dispatch`, com `if: github.ref == 'refs/heads/main'`. A `develop` não gera imagem |
| Matriz | `backend` (`Dockerfile.backend`, repositório em `vars.ECR_REPOSITORY_BACKEND`) e `frontend` (`Dockerfile.frontend`, `vars.ECR_REPOSITORY_FRONTEND`), com `fail-fast: false` |
| Environment | `production`, com `permissions: id-token: write` |
| Autenticação na AWS | OIDC (`vars.AWS_ROLE_ARN`, `vars.AWS_REGION`; o registry da Miggo fica em `us-east-2`), sem chave guardada |
| Tags | `<registry>/<repositório>:<sha do commit>` (imutável) e `:latest` |
| Plataforma | `vars.BUILD_PLATFORM`, padrão `linux/amd64` |
| Cache | buildx `type=gha`, com escopo por imagem |

Var de repositório vazia faz o job falhar com erro explícito (`vars.ECR_REPOSITORY_* vazia neste environment`). Nenhuma variável entra no build do frontend.

## Imagem do backend

`Dockerfile.backend`: `python:3.13-slim`, `libpq5`, `pip install -r backend/requirements.txt` e `playwright install --with-deps chromium` (o Chromium compõe o banner do LinkedIn e as capas de destaque a partir de HTML, MIG-409). Copia `backend/manage.py`, `backend/core` e `backend/apps` para `/app`, expõe `8000` (web) e `5555` (Flower) e usa `ENTRYPOINT ["/app/docker-entrypoint.sh"]`.

O `CMD` do web:

```bash
gunicorn core.wsgi:application --bind 0.0.0.0:8000 --worker-class gthread \
  --workers 3 --threads 8 --timeout 1800 --graceful-timeout 60 \
  --access-logfile - --error-logfile -
```

O timeout longo existe porque parte da geração ainda roda dentro do request; com o padrão de 30 s o Gunicorn aborta o worker no meio.

### Entrypoint: `ROLE`

`backend/docker-entrypoint.sh` escolhe o processo pela env `ROLE` (MIG-503). Web e worker usam **a mesma imagem**; o serviço de worker no Dokploy só muda a env.

| `ROLE` | O que sobe |
| --- | --- |
| ausente ou `web` | `migrate --noinput`, `seed_prompts`, `collectstatic --noinput`, Flower em segundo plano e `exec` do `CMD` |
| `worker` | `celery -A core worker -Q ia_interativo,ia_lote,composicao,entrega -l info -E --concurrency ${CELERY_WORKER_CONCURRENCY:-2} -n ia@%h --max-tasks-per-child 50 --max-memory-per-child 700000`, sem migrate, seed, collectstatic nem Flower |
| outro valor | recusa subir (`ROLE invalido`, `exit 1`) |

`seed_prompts` roda a cada subida do web porque os workflows (`title`, `image`, `caption`, `hashtags`) não vêm de data migration; o comando casa por chave natural e é idempotente.

**Flower no container do web.** O entrypoint sobe `python -m core.flower_guard` em segundo plano (porta `FLOWER_PORT`, padrão `5555`; `FLOWER_ADDRESS` padrão `0.0.0.0` no container). A guarda recusa subir sem `FLOWER_BASIC_AUTH` válida (`usuario:senha`, senha com 12 caracteres ou mais) e também recusa as opções que desligam a autenticação; nesse caso o web segue normalmente e o log mostra a recusa. O subshell do Flower sempre sai com `0`, para o Gunicorn não ler a morte dele como falha de boot. `FLOWER_ENABLED=0` desliga o Flower — defina no serviço de worker e no Flower avulso.

<Warning>
  `docker-entrypoint.sh` precisa de fim de linha LF (o `.gitattributes` força `*.sh text eol=lf`). Com CRLF o container morre com `/bin/sh^M: bad interpreter`.
</Warning>

### Variáveis que mudaram nesta imagem

| Variável | Para quê |
| --- | --- |
| `MIGGO_JWT_PUBLIC_KEY` | Chave pública RSA que valida o JWT emitido pelo `backend-miggo` (RS256). **Obrigatória**: lida em `core/settings.py` sem default, então o processo não sobe sem ela. Precisa ser o par da `JWT_PRIVATE_KEY` do backend |
| `REDIS_URL` | Broker e resultado do Celery. Ausente, as tasks rodam *eager* (no próprio processo) |
| `ROLE` | `worker` só no serviço de worker |
| `FLOWER_BASIC_AUTH` | Credencial do Flower; ausente, o Flower não sobe |
| `GRID_ASYNC`, `FILA_ASYNC`, `PERFIL_ASYNC` | Ligam grid, rodada/entrega e peças de perfil em fila; só valem com `REDIS_URL` |

Lista completa e defaults: `backend/.env.example` e `docs/celery.md` no repositório. Veja também [Configuração](/miggoai/configuracao).

<Note>
  `MIGGO_JWT_PUBLIC_KEY` não aparece no `backend/.env.example` da `main`; a obrigatoriedade vem do `config('MIGGO_JWT_PUBLIC_KEY')` nas settings.
</Note>

## Imagem do frontend

`Dockerfile.frontend`: build em `node:22-alpine` (`npm ci` e `npm run build`) e estágio final em `nginx:alpine`, com `frontend/nginx.conf` no lugar do `default.conf`.

A URL da API **não** entra no build. Um script em `/docker-entrypoint.d/40-miggo-config.sh` roda no start do Nginx e grava `/usr/share/nginx/html/config.js` com `window.__MIGGO_CONFIG__ = { API_BASE_URL: ... }`, a partir da env `VITE_API_BASE_URL` do container (padrão `http://localhost:8010`). O `index.html` carrega `/config.js` antes do bundle. A mesma imagem serve qualquer ambiente.

| `location` | Cache |
| --- | --- |
| `/` | `try_files $uri $uri/ /index.html` (deep link do react-router) |
| `= /config.js` | `no-store` (muda por ambiente) |
| `= /index.html` | `no-cache` (aponta para os assets com hash) |
| `/assets/` | `public, max-age=31536000, immutable` |
