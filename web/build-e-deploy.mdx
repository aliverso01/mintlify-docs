## O build

```bash
npm run build   # tsc -b && vite build
```

O comando roda em duas etapas: `tsc -b` verifica os tipos de todo o projeto e, só se passar, o Vite gera o bundle em `dist/`. A saída contém o `index.html`, os assets com hash e os SVGs processados pelo `vite-plugin-svgr`.

<Warning>
  Variáveis `VITE_*` são resolvidas **em tempo de build** e ficam gravadas no bundle. Trocar o `.env` sem reconstruir a imagem não muda nada em produção — e qualquer valor colocado ali é **público**, legível por quem abrir o DevTools. Nunca coloque segredo de servidor em `VITE_*`.
</Warning>

## Imagem Docker

O `dockerfile` usa build em dois estágios:

<Steps>
  <Step title="Estágio de build — node:20-alpine">
    ```dockerfile
    FROM node:20-alpine AS build
    WORKDIR /app
    COPY package*.json ./
    RUN npm install
    COPY . .
    ARG VITE_API_BASE_URL
    ENV VITE_API_BASE_URL=$VITE_API_BASE_URL
    RUN npm run build
    ```
    `VITE_API_BASE_URL` entra como **build arg**. As demais `VITE_*` chegam ao build pelo `.env.production` que o workflow de CI grava antes do `docker build` (veja abaixo); o `.dockerignore` exclui só `.env` e `.env.local`.
  </Step>
  <Step title="Estágio final — nginx:stable-alpine">
    Copia `dist/` para `/usr/share/nginx/html`, o `nginx.conf.template` para `/etc/nginx/`, e o `docker-entrypoint.sh` como entrypoint. Expõe a porta `80`.
  </Step>
</Steps>

## Build da imagem no ECR (GitHub Actions)

A imagem de produção é construída pelo workflow `.github/workflows/docker-ecr.yml` e publicada no **Amazon ECR**. O workflow **não faz deploy**: a troca de versão no Dokploy continua manual.

| Item | Como está no workflow |
| --- | --- |
| Gatilho | `push` na `main` e `workflow_dispatch`, com `if: github.ref == 'refs/heads/main'`. A `develop` não gera imagem |
| Environment | `production`, com `permissions: id-token: write` |
| Autenticação na AWS | OIDC (`vars.AWS_ROLE_ARN`, `vars.AWS_REGION`; o registry da Miggo fica em `us-east-2`), sem chave guardada |
| Tags | `<registry>/<ECR_REPOSITORY>:<sha do commit>` e `:latest` |
| Plataforma | `vars.BUILD_PLATFORM`, padrão `linux/amd64` |
| Build arg | `VITE_API_BASE_URL` vindo de `vars.VITE_API_BASE_URL` |

Antes do build, o passo "Gerar .env.production" escreve no `.env.production` as `VITE_*` definidas nas `vars` do environment (as vazias ficam de fora): `VITE_GOOGLE_CLIENT_ID`, `VITE_HELP_CENTER_URL`, `VITE_JWT_REFRESH_URL`, `VITE_CLARITY_PROJECT_ID` e `VITE_MIGGOAI_API_URL`. O log do job lista só os **nomes** definidos.

<Warning>
  O bundle de produção é montado **no GitHub**, não no servidor: para mudar uma `VITE_*` em produção, altere a `var` do environment `production` e gere a imagem de novo. Mudar a env no Dokploy não chega ao bundle. Segredo nenhum entra aqui: tudo em `VITE_*` é público.
</Warning>

`PROXY_HOST_TOKEN` **não** é variável de build: é lida pelo `docker-entrypoint.sh` em runtime (env do container no Dokploy) e vai só para a config do Nginx.

## Configuração do Nginx em tempo de execução

O `docker-entrypoint.sh` resolve o endereço do backend na subida do container:

```sh
BACKEND_URL="${VITE_API_BASE_URL}"
BACKEND_HOST=$(echo "$BACKEND_URL" | sed 's|https\?://||' | cut -d'/' -f1)
PROXY_HOST_TOKEN="${PROXY_HOST_TOKEN:-}"
export BACKEND_URL BACKEND_HOST PROXY_HOST_TOKEN
envsubst '${BACKEND_URL} ${BACKEND_HOST} ${PROXY_HOST_TOKEN}' \
    < /etc/nginx/nginx.conf.template \
    > /etc/nginx/conf.d/default.conf
exec nginx -g 'daemon off;'
```

Ele deriva o host a partir da URL, substitui os três placeholders no template com `envsubst` e sobe o Nginx em primeiro plano.

<Note>
  `VITE_API_BASE_URL` é usada **duas vezes e em momentos diferentes**: como build arg, para o bundle, e como variável de runtime, para montar o proxy do Nginx. Precisa estar definida nos dois lugares.
</Note>

### O que o template configura

`nginx.conf.template`:

| Bloco | Configuração |
| --- | --- |
| `listen` | Porta `80` |
| Upload | `client_max_body_size 50M` — necessário para vídeos e PDFs |
| SPA | `location /` com `try_files $uri $uri/ /index.html`, para o roteamento client-side do React Router |
| Proxy da API | `location /api` com `proxy_pass $backend` |
| Headers | `Host: ${BACKEND_HOST}`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto` |
| Host da agência | `X-Miggo-Host: $host` e `X-Miggo-Proxy-Token: ${PROXY_HOST_TOKEN}` no `/api`. A Plataforma só confia no host quando o token confere; sem token, trata como host Miggo. `proxy_set_header` substitui o que o cliente mandar, então não dá para forjar |
| Marca por host | `location = /index.html` com `ssi on` (só HTML, `ssi_silent_errors on`, `Cache-Control: no-cache`) e `location = /api/v1/agency/meta-tags/`, que repassa host e token com `Accept-Encoding` vazio, para o include das meta-tags da marca da agência |
| WebSocket | `proxy_http_version 1.1` com `Upgrade` e `Connection: upgrade` |
| TLS para Cloudflare | `proxy_ssl_server_name on`, `proxy_ssl_name ${BACKEND_HOST}`, `proxy_ssl_session_reuse off`, `proxy_ssl_protocols TLSv1.2 TLSv1.3` |
| DNS | `resolver 8.8.8.8 8.8.4.4 valid=300s`, `resolver_timeout 5s` |
| Timeouts | `proxy_connect_timeout`, `proxy_send_timeout` e `proxy_read_timeout` em `120s`, para uploads grandes |
| Buffer | `proxy_request_buffering off`, para uploads binários grandes |
| Erros | `error_page 500 502 503 504 /50x.html` |

<Warning>
  O limite de upload que vale para quem passa pelo web app é o `client_max_body_size` de **50 MB** deste Nginx, menor que o da Plataforma. Se um upload grande falhar só em produção, confira este número primeiro.
</Warning>

Existe também um `nginx.conf` no repositório, sem placeholders — o que a imagem usa é o **`.template`** processado pelo entrypoint.

## Publicar uma versão

<Steps>
  <Step title="Merge na main">
    O push na `main` dispara o `docker-ecr.yml`. A `develop` não gera imagem.
  </Step>
  <Step title="Imagem no ECR">
    O job publica `<ECR_REPOSITORY>:<sha do commit>` e `:latest`. Confira o job verde no GitHub Actions antes de seguir.
  </Step>
  <Step title="Troca no Dokploy (manual)">
    O workflow não faz deploy. No Dokploy, aponte o app do frontend para a imagem nova (de preferência a tag `:<sha>`, que identifica o commit) e reinicie. As variáveis de runtime (`VITE_API_BASE_URL`, `PROXY_HOST_TOKEN`) ficam no app do Dokploy.
  </Step>
  <Step title="Conferir">
    Abra `https://app.miggomkt.com.br`, faça login e confira uma chamada a `/api/*` e o painel de IA no `/admin/miggoai`.
  </Step>
</Steps>

Os domínios de cada ambiente estão em [Ambientes](/arquitetura/ambientes).

## Compose e Traefik

`docker-compose.yml` define o serviço `miggo-frontend`:

```yaml
build:
  context: .
  args:
    - VITE_API_BASE_URL
env_file: .env
restart: always
networks: [root_default]
```

Rótulos Traefik:

| Rótulo | Valor |
| --- | --- |
| Regra de host | `plataforma.miggomkt.com.br` (domínio anterior; `app.miggomkt.com.br` não aparece no compose versionado), mais um router catch-all (`HostRegexp`, prioridade 1) para os domínios de agência |
| Entrypoint | `websecure` |
| Certificado | `letsencrypt` |
| Porta interna | `80` |
| Middleware | `frontend-headers`, injetando `X-Forwarded-Proto: https` |

Domínios de agência entram por um segundo router, `miggo-web-agencias`: regra `HostRegexp` casando qualquer host (`.+`, sintaxe Traefik v3) com `priority=1`, para só pegar o host que nenhum outro router pegou; `tls=true` **sem** `certresolver` (o TLS termina na Cloudflare) e o mesmo serviço `miggo-web`. O fallback origin do Cloudflare for SaaS apontando para este servidor é passo manual.

A rede `root_default` é **externa**: precisa existir antes de subir o serviço.

## Passo a passo de subida

<Steps>
  <Step title="Preencher o .env">
    Na máquina de deploy, com as chaves de `.env.example` (`VITE_API_BASE_URL`, `VITE_JWT_REFRESH_URL`, `VITE_GOOGLE_CLIENT_ID`, `VITE_HELP_CENTER_URL`, `VITE_CLARITY_PROJECT_ID`), mais `VITE_MIGGOAI_API_URL` e, em runtime, `PROXY_HOST_TOKEN`. Em produção a imagem vem pronta do ECR; este roteiro vale para build fora do CI.
  </Step>
  <Step title="Construir com os build args">
    ```bash
    docker compose build
    ```
    O Compose passa os args a partir do ambiente. Confirme que as variáveis estão exportadas na sessão, não só no `.env`.
  </Step>
  <Step title="Subir">
    ```bash
    docker compose up -d
    ```
  </Step>
  <Step title="Conferir">
    O domínio deve responder com o SPA, `/api/*` deve chegar ao backend, e o login deve funcionar. Se a API responder 4xx de origem, verifique `CORS_ALLOWED_ORIGINS` e `CSRF_TRUSTED_ORIGINS` no backend.
  </Step>
</Steps>

## Desenvolvimento: o proxy do Vite

Em `npm run dev` o papel do Nginx é feito pelo `vite.config.ts`, que também encaminha `/api` para `VITE_API_BASE_URL`:

| Opção | Valor | Por quê |
| --- | --- | --- |
| `target` | `env.VITE_API_BASE_URL` | Backend local ou remoto |
| `changeOrigin` | `true` | Reescreve o header `Host` |
| `secure` | `false` | Aceita certificado autoassinado |
| `cookieDomainRewrite` | `"localhost"` | Faz o cookie de sessão valer no dev server |
| `configure` | Define `Origin` e `Referer` como o próprio target; repassa `X-Miggo-Host` (host original, sem porta) e, se houver `PROXY_HOST_TOKEN` no `.env`, `X-Miggo-Proxy-Token` | Passa pela validação de CSRF/CORS do Django e faz o papel do Nginx no domínio de agência |
| `allowedHosts` | `[".localhost"]` | `<slug>.localhost` resolve para 127.0.0.1 sem DNS e entra no dev server |

`PROXY_HOST_TOKEN` é lido pelo `vite.config.ts` **sem** prefixo `VITE_` de propósito: não vai para o bundle.

<Tip>
  Essa reescrita de `Origin` e `Referer` é o que permite desenvolver contra um backend remoto sem liberar `localhost` no `CSRF_TRUSTED_ORIGINS` dele.
</Tip>
