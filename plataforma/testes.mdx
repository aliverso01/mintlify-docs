O `backend-miggo` usa o test runner padrão do Django (`django.test.TestCase` / `APITestCase` do DRF). Os testes ficam dentro de cada app, em `app/<app>/tests.py` ou em módulos `tests_*.py` no mesmo diretório — não existe uma pasta central `tests/` no projeto.

<Warning>
Não confunda com a pasta `testes/` na raiz do repo (`testes/`). Ela **não** é a suíte automatizada: é uma coleção de scripts soltos (`populate_all.py`, `stripe_tests.py`, `tests_manychat.py`, etc.) que fazem chamadas reais a serviços externos (Stripe, ManyChat) e são executados manualmente com `python testes/<script>.py`, não com `manage.py test`. `testes/tests_manychat.py:1-6`, por exemplo, lê `MANYCHAT_API_KEY` via `decouple.config` e chama a API real do ManyChat — não é seguro nem seria correto incluí-lo numa rodada de CI. O único uso documentado dessa pasta no `README.md:8` é `python testes/populate_all.py`, para popular o banco após a configuração inicial do projeto.
</Warning>

## Como rodar

```bash
cd backend-miggo
./venv/Scripts/python.exe manage.py test
```

Para rodar só um app ou uma classe específica:

```bash
./venv/Scripts/python.exe manage.py test app.subscription
./venv/Scripts/python.exe manage.py test app.subscription.tests.FaturaDaStripeTests
```

<Warning>
`manage.py test` cria (e depois destrói) um banco de teste no Postgres. No ambiente local isso pode falhar por permissão do usuário do Postgres configurado em `DB_USER`/`DB_PASSWORD` (env vars lidas em `core/settings.py:207-211`), que muitas vezes não tem `CREATEDB` — o comando aborta antes de rodar qualquer teste.

**Alternativa que não depende de criar o banco de teste:**

```bash
# 1. valida que a configuração do Django carrega sem erro
./venv/Scripts/python.exe manage.py check

# 2. importa isoladamente o(s) módulo(s) alterado(s) para pegar erro de sintaxe/import
./venv/Scripts/python.exe -c "import django; django.setup(); from app.subscription import views"
./venv/Scripts/python.exe -c "import django; django.setup(); from app.subscription import cron, serializers"
```

Isso não substitui a suíte — só garante que o app importa e que a configuração do Django é válida. Sempre que possível, rode `manage.py test` de fato (em CI, ou em uma conta de Postgres com permissão de `CREATEDB`).
</Warning>

## O que NÃO está coberto

<Warning>
Os seguintes apps do projeto (`app/`) **não têm nenhum teste efetivo**:

- **`agenda`** — nenhum arquivo `tests*.py` no diretório.
- **`history`** — nenhum arquivo `tests*.py` no diretório.
- **`notification`** — nenhum arquivo `tests*.py` no diretório.
- **`integration`** — tem `app/integration/tests.py`, mas é só o boilerplate do `startapp` (3 linhas, nenhuma classe/teste).
- **`webhooks`** — mesma situação: `app/webhooks/tests.py` (3 linhas) só tem o boilerplate, apesar de `app/webhooks/views.py` concentrar os webhooks de pagamento da Stripe e da conta Zernio (críticos para o fluxo de cobrança).
</Warning>

<Note>
`webhooks` sem teste chama atenção porque é onde vive `webhook_stripe` (`core/urls.py:52`), o endpoint que processa eventos de cobrança em produção — qualquer regressão ali não é pega pela suíte automatizada.
</Note>
