## Responsabilidade

O app `app.integration` define um único model, `Integration`, usado como **log de auditoria genérico de chamadas a serviços externos**. Ele não é escrito pelo próprio app: dezenas de outros módulos do backend (`app.subscription`, `app.post`, `app.client`, `app.webhooks`, `app.onboarding`, `app.conversation`, `app.media`, `app.account`) chamam `Integration.objects.create(...)` diretamente sempre que fazem uma chamada de saída (Stripe, ManyChat, Instagram Graph API, Zernio, MiggoAI, Jira etc.), registrando serviço, rota, payload, resposta e status HTTP. O app em si só expõe a leitura/exclusão desse log via API REST.

<Note>
Confirmado por uso real no código — não é suposição: `Integration.objects.create(...)` aparece, por exemplo, em `app/subscription/views.py:301` (Stripe), `app/post/services.py:29-37` (ManyChat), `app/client/instagram.py:117` (Instagram), `app/post/zernio.py:248` (Zernio), `app/onboarding/miggoai.py:43` (MiggoAI) e `app/account/jira_service.py:72` (Jira).
</Note>

## Modelos

### Integration

`app/integration/models.py:5-20`

| Campo | Tipo | Obrigatório | Default/Choices | Descrição |
|---|---|---|---|---|
| `client` | `ForeignKey(Client)` | Não | `null=True, blank=True`, `on_delete=CASCADE` | Cliente ao qual a chamada se relaciona; `None` para chamadas não atreladas a um cliente específico (ex.: sync administrativo) |
| `service` | `CharField(max_length=255)` | Sim | — | Nome do serviço externo (ex.: `"Stripe"`, `"ManyChat"`) — string livre, não é `choices` |
| `path` | `TextField` | Sim | — | Rota/endpoint chamado no serviço externo |
| `method` | `CharField(max_length=50)` | Sim | — | Método/verbo da chamada — string livre; em alguns pontos de uso é um verbo HTTP (`POST`), em outros um rótulo semântico (ex.: `POST_WHATSAPP` em `app/post/services.py:36`) |
| `payload` | `JSONField` | Não | `null=True, blank=True` | Corpo/parâmetros enviados na chamada |
| `response` | `JSONField` | Não | `null=True, blank=True` | Resposta recebida do serviço externo |
| `status_code` | `IntegerField` | Não | `null=True, blank=True` | Código HTTP (ou equivalente) da resposta |
| `created_at` | `DateTimeField` | Auto | `auto_now_add=True` | Timestamp de criação do registro |
| `updated_at` | `DateTimeField` | Auto | `auto_now=True` | Atualizado a cada `save()` — na prática, os pontos de uso encontrados só fazem `Integration.objects.create(...)`, não atualizam depois |

Não há relação reversa nomeada (`related_name`) declarada em `client` — o acesso a partir de `Client` usa o related manager default (`integration_set`).

**Métodos**: `__str__` (`app/integration/models.py:16-20`) retorna `"{method} - {service} - {client.name} - {created_at:%d-%m-%Y - %H:%M}"` quando há `client`, ou a mesma string sem o nome do cliente quando `client` é `None`.

## Endpoints

Prefixo: `api/v1/integration/` (`core/urls.py:33`).

| Método | Rota completa | View | Permissão |
|---|---|---|---|
| GET | `api/v1/integration/list/` | `IntegrationListView` | `IsManagementUser` (bloqueia `role='client'`; aceita API key de serviço ou equipe) |
| GET | `api/v1/integration/detail/<int:pk>/` | `IntegrationDetailView` | Default do projeto — `HasAPIKeyOrIsAuthenticated` (sem `permission_classes` própria) |
| DELETE | `api/v1/integration/delete/<int:pk>/` | `IntegrationDeleteView` | Default do projeto — `HasAPIKeyOrIsAuthenticated` (sem `permission_classes` própria) |

<Warning>
Apenas `IntegrationListView` restringe a equipe (`IsManagementUser`, `app/integration/views.py:14`). `IntegrationDetailView` e `IntegrationDeleteView` não declaram `permission_classes` e caem no default global `HasAPIKeyOrIsAuthenticated` (`core/settings.py:139-141`) — qualquer usuário autenticado, inclusive `role='client'`, pode ler ou **apagar** um registro de log de integração pelo `pk` se souber (ou adivinhar) o id. Como o log pode conter `payload`/`response` de chamadas a serviços como Stripe, isso é um ponto sensível — ver [Erros comuns](#erros-comuns-pontos-de-atencao).
</Warning>

## Regras de negócio e funções

Este app não define signals, middleware nem management commands próprios — `IntegrationConfig` (`app/integration/apps.py:4-6`) não sobrescreve `ready()`.

A "regra de negócio" real do model é o **padrão de uso disperso pelo resto do backend**: cada integração externa chama `Integration.objects.create(...)` manualmente no ponto onde faz a chamada de saída, para registrar o que foi enviado e o que voltou. Exemplos confirmados no código:

- `app/subscription/views.py:301-312` — chamadas ao Stripe (criação/atualização de customer), gravando `service='Stripe'`, `path`, `method`, `payload`, `response`, `status_code`.
- `app/post/services.py:28-37` — função utilitária `_log(client, path, payload, response_data, status_code)` que centraliza o registro das chamadas ao ManyChat (`service='ManyChat'`) dentro do módulo de posts.
- `app/client/instagram.py:117` — chamadas à API do Instagram.
- `app/post/zernio.py:248` — chamadas ao Zernio (agendador externo).
- `app/onboarding/miggoai.py:43` — chamadas ao serviço MiggoAI durante o onboarding.
- `app/account/jira_service.py:72` — chamadas ao Jira.
- Também usado em `app/webhooks/views.py`, `app/media/cron.py`, `app/subscription/cron.py`, `app/onboarding/cron.py`, `app/onboarding/services.py` e extensivamente em `app/post/views.py`.

<Note>
Não há uma função/serviço central (tipo `log_integration_call()`) reaproveitada por todos esses pontos — cada app chama `Integration.objects.create(...)` diretamente com seus próprios campos, exceto `app/post/services.py`, que encapsula a chamada numa função privada `_log`. Isso significa que a consistência de `service`/`method` entre chamadas depende de cada desenvolvedor seguir a convenção, não de um contrato de código.
</Note>

## Erros comuns / pontos de atenção

- **`IntegrationDetailView` e `IntegrationDeleteView` não exigem `IsManagementUser`.** Só `IntegrationListView` restringe a equipe; as outras duas caem no default `HasAPIKeyOrIsAuthenticated`, que aceita qualquer usuário autenticado — incluindo clientes (`role='client'`). Um cliente autenticado que descobrir um `pk` pode ler ou apagar um log de integração de qualquer cliente, não só o seu (não há filtro por `client` dono da sessão). Vale confirmar se isso é intencional.
- **`payload`/`response` podem conter dados sensíveis.** Como o log grava o corpo bruto das chamadas a serviços como Stripe, é preciso cuidado ao expor esses campos via `IntegrationDetailView`/`IntegrationListView` — não há mascaramento de campos sensíveis no serializer.
- **`method` não é padronizado.** Nem sempre é um verbo HTTP — em `app/post/services.py:36` o valor gravado é `'POST_WHATSAPP'`, um rótulo semântico. Filtros ou dashboards que assumem `method` como verbo HTTP puro vão falhar para esses registros.
- **Sem paginação/filtro por client na exclusão.** `IntegrationDeleteView` apaga um registro por vez, sem confirmação nem auditoria da própria exclusão (o app não tem "quem apagou o log").
- **Não há testes.** `app/integration/tests.py` está vazio — nenhuma cobertura automatizada para este app.
