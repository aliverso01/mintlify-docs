## Responsabilidade

O app `app.emailmarketing` implementa a "régua" de e-mails de marketing/trial da Miggo (MIG-264): campanhas escritas pela equipe na área `/admin`, que disparam automaticamente quando um cliente atinge um **evento do ciclo de vida** (cadastro, onboarding concluído, fim do trial) somado a um **deslocamento em dias** — ou, para campanhas avulsas, numa **data marcada**. O disparo em si é feito pelo management command `send_marketing_emails`, agendado externamente (Dokploy); o app não tem cron/scheduler embutido.

O motivo de usar "evento + dias" em vez de "dia N do trial" está documentado no próprio código: as duas versões do "dia 0" (novo cadastro x onboarding concluído) partem de momentos diferentes da vida do cliente (`app/emailmarketing/models.py:10-13`).

Registrado em `INSTALLED_APPS` como `app.emailmarketing.apps.EmailMarketingConfig` (`core/settings.py:131`) e montado em `core/urls.py:43` sob o prefixo:

```
/api/v1/email-marketing/
```

## Regras de negócio e funções

Toda a lógica de público, rastreio e envio vive em `app/emailmarketing/services.py`; os management commands apenas orquestram e reportam.

### Rastreio de clique

- **`assinar_destino(url)`** (`services.py:60-64`): assinatura HMAC-SHA256 do destino usando `settings.SECRET_KEY`, truncada em 20 caracteres hex. Retorno: `str`.
- **`destino_valido(url, assinatura)`** (`services.py:67-68`): compara com `hmac.compare_digest` contra `assinar_destino(url)`. Retorno: `bool`.
- **`_url_de_rastreio(token, destino)`** (`services.py:71-74`, privada): monta `{BACKEND_URL}/api/v1/email-marketing/click/{token}/?to=...&s=...`.
- **`aplicar_rastreio(html, token)`** (`services.py:77-92`): substitui todo `href="http(s)://..."` do corpo (via regex `_HREF_RE`) pelo link rastreado. Se `settings.BACKEND_URL` não estiver configurado, loga um warning e devolve o HTML **sem** rastreio — preferem perder a métrica a mandar um e-mail com botões quebrados por link relativo.

Sem verificação de assinatura, a rota de clique seria um redirecionador aberto no domínio da Miggo — risco de phishing e de o domínio ser bloqueado (`services.py:53-55`, `views.py:126-129`).

### Limites de frequência (privadas)

- **`_ultimo_envio_por_cliente(client_ids)`** (`services.py:97-108`): dict `{client_id: sent_at}` do envio `SENT` mais recente de cada cliente.
- **`_ignorados_seguidos_por_cliente(client_ids)`** (`services.py:111-133`): dict `{client_id: contagem}` de e-mails `SENT` seguidos sem clique, contados a partir do envio mais recente até o primeiro que teve clique (um clique zera a sequência, não é penalidade permanente).
- **`_onboarding_por_cliente(client_ids)`** (`services.py:136-140`): dict `{client_id: OnboardingSession}`.
- **`_fim_do_trial_por_cliente(client_ids)`** (`services.py:143-153`): dict `{client_id: expires_at}` da assinatura de teste (`Subscription.trial=True`) mais recente de cada cliente.

### `resolve_event_date(evento, client, sessao, fim_do_trial, campanha=None)`

`services.py:156-175`. Retorna a `date` (não `datetime`) em que o evento aconteceu para o cliente, ou `None` se ainda não ocorreu:
- `scheduled` → `campanha.scheduled_date` (mesma data para todos, vem da campanha).
- `signup` → data local de `client.created_at`.
- `onboarding_completed` → `None` se a sessão não existe ou `completed_at` é `None`; senão a data local de `completed_at`.
- `trial_end` → data local de `fim_do_trial`, ou `None`.

### `_passa_no_publico(campanha, sessao)`

`services.py:178-184`. `True`/`False` conforme `campanha.audience`: `all` sempre passa; `onboarding_done` exige `sessao.is_complete`; `onboarding_pending` exige o contrário.

### `destinatarios(campanha, hoje=None)`

`services.py:187-245`. **Função central de elegibilidade** — retorna a lista de `Client` que devem receber a campanha hoje e ainda não receberam.

1. Exclui clientes que já têm `EmailDispatch` com `status=SENT` para essa campanha, e clientes sem `email`.
2. Para cada cliente, resolve `data_evento` via `resolve_event_date`; se `None`, pula.
3. Calcula `data_alvo = data_evento + delay_days` (campanha `scheduled` usa deslocamento `0`).
4. Só considera elegível se `hoje - JANELA_DE_ATRASO_DIAS <= data_alvo <= hoje` (`JANELA_DE_ATRASO_DIAS = 3`, `services.py:48`) — tolera atraso de até 3 dias (ex.: deploy/manutenção) mas não dispara para toda a base histórica ao ativar uma campanha nova.
5. Filtra por público (`_passa_no_publico`).
6. Se `campanha.bypass_limits` for `False`: aplica teto de ignorados (`campanha.limite_de_ignorados`) e intervalo mínimo (`campanha.intervalo_minimo`), herdando de `EmailMarketingSettings.load()` quando a campanha não define valor próprio.

Retorno: `list[Client]`.

<Warning>
`JANELA_DE_ATRASO_DIAS = 3` é o teto que impede uma campanha recém-ativada de disparar para toda a base histórica de uma vez (todo cliente antigo tem data de cadastro) — comentário explícito em `services.py:40-48`. Ativar uma campanha `signup`/`onboarding_completed`/`trial_end` sem essa proteção "queimaria" a reputação do domínio de envio.
</Warning>

### `render_email(campanha, client)`

`services.py:248-256`. Monta o HTML final substituindo `{{ nome }}`/`{{nome}}` no `body_html` pelo `client.name`, e renderiza o template `emails/marketing_base.html` com `{subject, body_html, frontend_url}`. Retorno: `str` (HTML completo).

### `enviar_campanha(campanha, hoje=None, dry_run=False)`

`services.py:259-320`. Envia a campanha para quem está elegível hoje.

- Chama `destinatarios(campanha, hoje=hoje)`. Se vazio ou `dry_run=True`, retorna o resumo sem enviar nada.
- Abre **uma única conexão SMTP** (`get_connection()`) para todo o lote.
- Aplica rate limit: no máximo `RATE_LIMIT_PER_WINDOW = 50` envios por `RATE_LIMIT_WINDOW_SECONDS = 60` segundos (`services.py:36-37`); ao atingir o teto, dorme o tempo restante da janela antes de continuar.
- Para cada cliente: cria (ou reaproveita) um `EmailDispatch` via `get_or_create` com `status=PENDING` **antes** de enviar — é dali que sai o `token` dos links rastreados, e o `unique_together` impede dois processos concorrentes de enviarem duplicado. Se já existir um dispatch `SENT`, pula.
- Renderiza o HTML (`render_email` + `aplicar_rastreio`) e envia via `EmailMultiAlternatives` (corpo texto via `strip_tags`, alternativa HTML anexada).
- Em caso de exceção no envio: grava `status=FAILED` e `error` (truncado em 2000 chars), loga warning, incrementa `resumo['failed']` — uma falha de e-mail não interrompe o lote.
- Em caso de sucesso: `status=SENT`, `error=''`, incrementa `resumo['sent']`.
- Retorno: `dict {'campaign': str, 'eligible': int, 'sent': int, 'failed': int}`.

### `enviar_campanhas_ativas(hoje=None, dry_run=False)`

`services.py:323-327`. Chama `enviar_campanha` para cada `EmailCampaign` com `is_active=True`. Retorno: `list[dict]` (um resumo por campanha).

### Management command: `seed_marketing_emails`

`app/emailmarketing/management/commands/seed_marketing_emails.py`

- **O que faz:** cria/atualiza as 7 campanhas padrão da régua de trial descrita no card MIG-264 (dias 0, 1, 3, 4, 6, 7 e 8), com conteúdo HTML fixo definido no próprio comando (`CAMPANHAS`, `seed_marketing_emails.py:17-157`).
- **Idempotente:** identifica cada campanha pelo campo `name` e usa `EmailCampaign.objects.update_or_create(name=..., defaults=...)` (`seed_marketing_emails.py:167`) — rodar de novo atualiza o texto sem duplicar. O corpo permanece editável depois via `/admin`.
- **Argumentos:** nenhum.
- **Exemplo:**
  ```bash
  ./venv/Scripts/python.exe manage.py seed_marketing_emails
  ```
- Ao final imprime quantas campanhas foram criadas e quantas atualizadas.

### Management command: `send_marketing_emails`

`app/emailmarketing/management/commands/send_marketing_emails.py`

- **O que faz:** dispara as campanhas de e-mail marketing elegíveis no dia, chamando `services.enviar_campanhas_ativas` (ou `services.enviar_campanha` para uma campanha específica). Pensado para rodar uma vez por dia via schedule externo (Dokploy) — rodar duas vezes no mesmo dia não duplica envio, pois a trava é o `EmailDispatch` (`unique_together`).
- **Argumentos:**
  - `--dry-run`: só conta quem receberia, sem enviar nem gravar nada (`store_true`).
  - `--campaign <id>`: dispara apenas a campanha com esse id, em vez de todas as ativas. Se o id não existir, imprime erro e sai sem lançar exceção.
- **Exemplos:**
  ```bash
  ./venv/Scripts/python.exe manage.py send_marketing_emails
  ./venv/Scripts/python.exe manage.py send_marketing_emails --dry-run
  ./venv/Scripts/python.exe manage.py send_marketing_emails --campaign 3
  ```
- Ao final imprime, por campanha, elegíveis/enviados/falhos, e um total agregado; usa `self.style.WARNING` se houve alguma falha, `SUCCESS` caso contrário.

<Note>
Uma régua com 500 destinatários no mesmo dia leva cerca de 10 minutos de execução, dado o rate limit de 50/min — o comando é pensado para rodar sozinho, sem timeout apertado (`services.py:33-35`).
</Note>

## Erros comuns / pontos de atenção

<Warning>
Sem `settings.BACKEND_URL` configurado, os e-mails saem **sem rastreio de clique** (silenciosamente, só um warning no log) — `aplicar_rastreio` detecta a ausência e devolve o HTML original (`services.py:85-87`).
</Warning>

<Warning>
Ativar uma campanha ancorada em `signup`/`onboarding_completed`/`trial_end` dispara retroativamente para quem passou pelo evento nos últimos `JANELA_DE_ATRASO_DIAS` (3) dias — não para toda a base histórica, graças à janela, mas ainda é um disparo imediato a considerar antes de ativar.
</Warning>

<Warning>
`EmailCampaignPreviewView` e `EmailCampaignAudienceView` retornam `404` simples (`{'detail': 'Campanha não encontrada.'}`) quando o `pk` não existe — não há tratamento de permissão adicional por campanha, apenas `IsManagementUser` global.
</Warning>

<Note>
O comando `send_marketing_emails --campaign <id>` só existe para permitir reenvio pontual de uma campanha; ele ainda respeita todas as regras de elegibilidade normais (não força envio para quem já recebeu ou não é elegível hoje).
</Note>
