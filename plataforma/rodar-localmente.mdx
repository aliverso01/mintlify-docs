O `backend-miggo` é a API Django da plataforma. Este guia leva do clone a uma API respondendo em `http://localhost:8000`, com o mínimo de variáveis. A lista completa de variáveis está em [Variáveis de ambiente](/plataforma/configuracao).

## Pré-requisitos

| Ferramenta | Versão | Observação |
|---|---|---|
| Python | 3.11 ou mais novo | A imagem de produção e a CI usam **3.11**. Ao adicionar biblioteca, confira que ela tem *wheel* para 3.11 |
| PostgreSQL | 16 | O único banco configurado nas settings (`django.db.backends.postgresql`) |
| Redis | opcional | Só para testar o Celery de verdade. Sem `REDIS_URL` as tasks rodam no próprio processo |
| Chromium do Playwright | opcional | Último recurso da raspagem de site do onboarding, quando o site recusa o GET simples |

## Passo a passo

<Steps>
  <Step title="Clonar e criar a venv">
    ```bash
    git clone <url-do-repo> backend-miggo
    cd backend-miggo
    python -m venv venv
    source venv/bin/activate      # Linux/macOS
    venv\Scripts\activate         # Windows
    ```
  </Step>

  <Step title="Instalar as dependências">
    ```bash
    pip install -r requirements.txt
    playwright install --with-deps chromium   # opcional
    ```

    <Note>
      O `requirements.txt` está salvo em UTF-16. Se o `pip` reclamar de caracteres inválidos, converta o arquivo para UTF-8 antes de instalar (`iconv -f UTF-16LE -t UTF-8`).
    </Note>
  </Step>

  <Step title="Criar o banco">
    Use um Postgres local ou o serviço `miggo-db` do `docker-compose.yml`. Crie o banco e o usuário que vão nas variáveis `DB_*`.
  </Step>

  <Step title="Criar o .env">
    Copie a lista de chaves do `.env.example` (todas vêm sem valor) e preencha pelo menos as obrigatórias:

    ```bash
    cp .env.example .env
    ```

    ```bash .env
    DEBUG=True
    DB_NAME=miggo
    DB_USER=miggo
    DB_PASSWORD=<senha>
    DB_HOST=localhost
    DB_PORT=5432
    EMAIL_HOST=localhost
    EMAIL_PORT=1025
    EMAIL_HOST_USER=<usuario>
    EMAIL_HOST_PASSWORD=<senha>
    MIGGO_API_KEY=<qualquer-valor-local>
    JWT_PRIVATE_KEY=<chave-privada-rsa-em-uma-linha>
    ```

    A `JWT_PRIVATE_KEY` não está no `.env.example`, mas as settings não carregam sem ela. Gere uma chave descartável para desenvolvimento:

    ```bash
    openssl genrsa 2048 | awk 'BEGIN{ORS="\\n"} {print}'
    ```

    O comando imprime o PEM em uma linha, com `\n` literal no lugar das quebras, que é o formato que as settings esperam.

    <Warning>
      Não use chaves de produção no ambiente local. Integrações (Stripe, ManyChat, Zernio, OpenAI) ficam de fora até você precisar delas: quase todas têm default vazio e o código trata a ausência.
    </Warning>
  </Step>

  <Step title="Aplicar as migrations">
    ```bash
    python manage.py migrate
    ```
  </Step>

  <Step title="Criar um usuário administrador">
    ```bash
    python manage.py createsuperuser
    ```

    O login é por e-mail (`account.CustomUser`); o comando pede `email`, `name` e senha. O superusuário nasce com `role='admin'`.
  </Step>

  <Step title="Popular os dados básicos (opcional)">
    ```bash
    python testes/populate_all.py
    ```

    Cria formatos, status de post, planos e demais tabelas de catálogo que as telas esperam encontrar.
  </Step>

  <Step title="Subir a API">
    ```bash
    python manage.py runserver 8000
    ```

    Confira:

    ```bash
    curl http://localhost:8000/health/
    ```

    A documentação interativa do schema fica em `http://localhost:8000/api/schema/swagger-ui/`.
  </Step>
</Steps>

## Worker do Celery (opcional)

Sem `REDIS_URL`, o Celery roda em modo *eager*: a task executa dentro do próprio request ou command, e nada precisa subir. Para testar a fila de verdade:

```bash
# .env
REDIS_URL=redis://localhost:6379
ONBOARDING_ASYNC=1   # e as demais flags do fluxo que for testar

# em outro terminal
celery -A core worker -Q interativo,integracoes,leve -l info
python manage.py celery_ping
```

Filas, flags e limites: [Filas e Celery](/plataforma/filas-e-celery).

## Rotinas agendadas em desenvolvimento

Em produção, as rotinas são management commands chamados pelos Schedules do Dokploy. Localmente, rode o comando que quiser testar:

```bash
python manage.py expire_trials
```

O `run_cron.py` da raiz roda em laço um subconjunto das rotinas (cobrança e revisões agendadas), com intervalos curtos para teste. Veja [Tarefas agendadas](/plataforma/tarefas-agendadas).

## Problemas comuns

<AccordionGroup>
  <Accordion title="O manage.py não sobe e reclama de DEBUG ou JWT_PRIVATE_KEY">
    `DEBUG`, as `DB_*`, as `EMAIL_*` (menos TLS/SSL), `MIGGO_API_KEY` e `JWT_PRIVATE_KEY` não têm valor padrão. Sem qualquer uma delas a importação das settings falha.
  </Accordion>
  <Accordion title="manage.py test não cria o banco de teste">
    O usuário do Postgres local costuma não ter permissão de `CREATEDB`. Rode a suíte com um settings de teste em SQLite: veja [Testes](/plataforma/testes).
  </Accordion>
  <Accordion title="Login com Google falha com 'Token used too early'">
    Diferença de relógio entre a máquina e o Google. Aumente `GOOGLE_AUTH_CLOCK_SKEW` (padrão: 10 segundos).
  </Accordion>
  <Accordion title="Raspagem de site falha com 'navegador de leitura não está disponível'">
    Falta o Chromium do Playwright. Rode `playwright install --with-deps chromium`.
  </Accordion>
  <Accordion title="O front local não consegue chamar a API">
    Confira `CSRF_TRUSTED_ORIGINS` (padrão `http://localhost:5173`) e `CORS_ALLOWED_ORIGINS` (padrão `*`). Veja [Rodar o web app localmente](/web/rodar-localmente).
  </Accordion>
</AccordionGroup>
