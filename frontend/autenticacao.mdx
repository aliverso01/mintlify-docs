A autenticação é por **JWT puro** (access + refresh), armazenado em `localStorage` e injetado automaticamente em todo `fetch` para `/api/*` por um interceptor global instalado em `src/main.tsx:12`.

## Armazenamento de token (`src/services/jwtAuth.ts`)

Chaves de `localStorage`: `miggo_access_token`, `miggo_refresh_token`, `user` (`jwtAuth.ts:1-3`).

### Funções exportadas

| Função | Assinatura | Retorno / efeito |
|---|---|---|
| `getAccessToken` | `(): string` | Lê `miggo_access_token` do `localStorage`, ou `""` (`jwtAuth.ts:40-42`) |
| `getRefreshToken` | `(): string` | Lê `miggo_refresh_token`, ou `""` (`jwtAuth.ts:44-46`) |
| `setTokens` | `(tokens: { accessToken: string; refreshToken?: string }): void` | Grava os tokens no `localStorage` (`jwtAuth.ts:48-53`) |
| `clearTokens` | `(): void` | Remove ambos os tokens (`jwtAuth.ts:55-58`) |
| `getAuthorizationHeader` | `(): string` | Devolve `"Bearer <token>"` ou `""` (`jwtAuth.ts:60-63`) |
| `saveTokensFromResponse` | `(data): Promise<boolean>` | Extrai access/refresh de um payload de resposta heterogêneo (`access`, `accessToken`, `access_token`, `token`, `jwt`, `tokens.access`, e equivalentes para refresh) e salva; retorna `false` se não achou access token (`jwtAuth.ts:25-73`) |
| `setupAuthFetchInterceptor` | `(): void` | Instala o interceptor global de `window.fetch` (idempotente via flag `fetchPatched`) (`jwtAuth.ts:179-248`) |

### O interceptor de `fetch` (`setupAuthFetchInterceptor`)

Chamado uma única vez em `src/main.tsx:12`, antes do primeiro render. Para cada `fetch`:

1. Identifica se a requisição é para a própria API do app (`isApiRequest`: mesma origem + path iniciando em `/api/`) e se é um endpoint de auth (`login/`, `token/`, `token/refresh/`, `register/`, `google/`) — `jwtAuth.ts:194-204`.
2. **Refresh proativo**: para requests de API que não são de auth, chama `ensureFreshAccessToken` antes de disparar — se o access token está a menos de 15s de expirar (`isAccessTokenExpired`, skew configurável), dispara um refresh e só então segue (`jwtAuth.ts:90-96,173-177,209-211`).
3. Descarta qualquer `Authorization` não-Bearer em requests da própria API (ex.: `Api-Key`, exclusivo de serviços de terceiros) e injeta `Bearer <access token>` quando há token (`jwtAuth.ts:213-227`).
4. **Fallback reativo**: se a resposta vier `401` (e não for endpoint de auth, e ainda não houve retry), tenta um refresh e repete a mesma requisição uma única vez (`jwtAuth.ts:233-244`).

### Refresh do token

`refreshAccessToken` (`jwtAuth.ts:119-168`) é **deduplicado** via uma Promise compartilhada (`refreshInFlight`): se várias requisições expiram ao mesmo tempo, todas aguardam o mesmo POST para `VITE_JWT_REFRESH_URL` (default `/api/v1/account/token/refresh/`) em vez de disparar um refresh cada — evita invalidar um refresh token rotativo no backend por corrida.

Se o refresh falhar (sem refresh token, resposta não-ok, ou erro de rede), chama `forceSignOut()`: limpa tokens + `user` do `localStorage` e redireciona para `/signin` uma única vez (guarda `redirectingToSignin` evita loop) (`jwtAuth.ts:99-111`).

## `AuthContext` (`src/context/AuthContext.tsx`)

Provider React que mantém `user`, `loading` e `error`, e expõe as operações de conta. Interface completa (`AuthContext.tsx:71-83`):

```ts
interface AuthContextType {
  user: User | null;
  loading: boolean;
  error: string | null;
  login: (credentials: { email: string; password?: string }) => Promise<void>;
  loginWithGoogle: (credential: string) => Promise<void>;
  logout: () => Promise<void>;
  updateProfile: (data: Partial<User>, verificationCode?: string) => Promise<void>;
  register: (data: { name: string; email: string; phone: string; password?: string }) => Promise<void>;
  requestPasswordReset: (email: string) => Promise<string>;
  confirmPasswordReset: (email: string, code: string, newPassword: string) => Promise<string>;
  requestVerificationCode: () => Promise<void>;
}
```

O tipo `User` (`AuthContext.tsx:55-69`) inclui `id`, `email`, `name`, `phone`, `role`, `is_staff`, `is_superuser`, `is_active`, `groups`, `user_permissions`, `created_at`, `last_login`, `hash`.

### Funções (endpoint + comportamento)

| Função | Endpoint | Comportamento |
|---|---|---|
| `login` | `POST /api/v1/account/login/` | Tenta extrair tokens da própria resposta (`saveTokensFromResponse`); se não vierem, faz um segundo `POST` para `VITE_JWT_OBTAIN_URL` (default `/api/v1/account/token/`). Salva `user` em estado e `localStorage`. Trata `403` (conta inativa) e `401` (credenciais inválidas) com mensagens específicas (`AuthContext.tsx:138-201`) |
| `loginWithGoogle` | `POST /api/v1/account/google/` com `{ credential }` | Mesmo fluxo de salvar tokens/usuário (`AuthContext.tsx:203-240`) |
| `logout` | `POST /api/v1/account/logout/` | Chama o backend (best-effort — erro é só logado) e sempre limpa `user`, tokens e `miggo_preview_mode` do `localStorage` (`AuthContext.tsx:242-260`) |
| `updateProfile` | `PATCH /api/v1/account/update/<user.id>/` | Aceita `verificationCode` opcional, que é anexado ao body como `verification_code` (`AuthContext.tsx:262-298`) |
| `register` | `POST /api/v1/account/register/` | Usa `parseDRFError` para traduzir erros de validação do DRF para pt-BR (`AuthContext.tsx:300-337`) |
| `requestPasswordReset` | `POST /api/v1/account/password-reset/request/` | Retorna a mensagem do backend (`AuthContext.tsx:339-350`) |
| `confirmPasswordReset` | `POST /api/v1/account/password-reset/confirm/` | Envia `{ email, code, new_password }` (`AuthContext.tsx:352-363`) |
| `requestVerificationCode` | `GET /api/v1/client/list/` (para achar o client do usuário) + `GET /api/v1/client/generate-activation-code/<clientId>/` | Usa `findOwnClient`/`toClientList` (`src/utils/clients.ts`) para localizar o cliente do usuário logado (`AuthContext.tsx:365-394`) |

### Tradução de erros do DRF

`parseDRFError` (`AuthContext.tsx:32-52`) e `translateDRFMsg` (`AuthContext.tsx:18-30`) convertem respostas de erro do Django REST Framework (`{detail}`, `{message}`, ou `{campo: ["erro"]}`) em texto pt-BR legível, com um mapa de rótulos de campo (`FIELD_LABELS`, `AuthContext.tsx:8-14`).

### Persistência e expiração

- Ao montar, lê `user` do `localStorage`; se houver `user` salvo mas nenhum access token, considera a sessão inválida (resquício de uma sessão legada por API key) e limpa tudo (`AuthContext.tsx:95-114`).
- Não há mais validação periódica ativa — o comentário no código explica que essa checagem foi desabilitada porque o JWT já é validado a cada request pelo backend; o logout efetivo acontece quando o interceptor recebe um `401` e o refresh falha (`AuthContext.tsx:117-136`).

### Preview mode e `effectiveUser`

Quando `PreviewContext.isPreviewMode` está ativo, `AuthContext` devolve um `effectiveUser` com `role: 'client'` e `id` substituído pelo `previewClientId` — toda a lógica de `role === 'client'` do resto do app passa a tratar o admin como o cliente sob preview, automaticamente (`AuthContext.tsx:399-408`).

## `useAuth` (`src/hooks/authHook.ts`)

Wrapper fino sobre `useAuthContext` que adiciona navegação pós-ação via `useNavigate` (`react-router`):

```ts
export const useAuth = () => {
  // ...
  return { login, loginWithGoogle, logout, user, loading, error, register, requestPasswordReset, confirmPasswordReset };
};
```

- `login`/`register`/`loginWithGoogle` navegam para `/` após sucesso (que por sua vez cai em `RoleHomeRedirect`) (`authHook.ts:18-45`).
- Erros de `login`/`register` são apenas logados no console (não relançados) exceto em `loginWithGoogle` e `register`, que relançam para o chamador tratar (`authHook.ts:22-24,32-34,42-44`).

<Note>
`useAuth` (hook) e `useAuthContext` (context) coexistem — a maioria das telas de negócio usa `useAuth`; componentes de infraestrutura de rota (guards, sidebar) usam `useAuthContext` diretamente quando não precisam da navegação embutida.
</Note>

## Login com Google (`@react-oauth/google`)

- `GoogleOAuthProvider` só envolve a árvore se `VITE_GOOGLE_CLIENT_ID` estiver definida (`src/main.tsx:16,30-34`).
- `SignInForm.tsx:23`, `SignUpForm.tsx:35` e `SignupStep.tsx:75` checam `isGoogleEnabled = Boolean(import.meta.env.VITE_GOOGLE_CLIENT_ID)` para decidir se mostram o botão.
- O `credential` retornado pelo Google é passado para `loginWithGoogle`, que o envia como `{ credential }` para `POST /api/v1/account/google/`.

## Resolução do papel do usuário (`useRoleArea`)

`src/hooks/useRoleArea.ts:18-33` combina `useAuth` com os helpers de `src/routes/rolePaths.ts`:

```ts
export function useRoleArea() {
  const { user, loading } = useAuth();
  return useMemo(() => ({
    loading,
    isManagement: isManagementUser(user),
    isFullAdmin: isFullAdminUser(user),
    isClient: isClientUser(user),
    prefix: areaPrefixFor(user),
    home: homePathFor(user),
    path: (subpath: string) => pathFor(user, subpath),
  }), [user, loading]);
}
```

Ver a lógica completa de `isManagementUser`/`isFullAdminUser`/`isClientUser`/`areaPrefixFor`/`pathFor` em `roteamento.mdx`.
