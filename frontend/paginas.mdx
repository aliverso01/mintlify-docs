Esta página cataloga as telas de `src/pages/` do `frontend-miggo`, exceto `Onboarding/` (ver `onboarding.mdx`) e `Admin/` (ver `area-admin.mdx`).

O roteamento vive em `src/App.tsx`. A maioria das telas é montada **duas vezes** — uma vez sob `/admin/*` (equipe Miggo, dentro de `ManagementRoute`) e outra sob `/app/*` (cliente final, dentro de `ClientRoute`) — com o **mesmo componente**, que decide internamente o que mostrar a partir do papel (`user.role`) obtido de `useAuthContext`/`useAuth`. Isso está documentado por tela abaixo.

<Note>
`src/pages/AuthPages/OnboardingFlow.tsx` (1060 linhas) existe no repositório mas **não é importado por `App.tsx`** — a rota `/onboarding` usa `src/pages/Onboarding/OnboardingShell.tsx`. Parece um arquivo órfão/legado; não documentado aqui como tela ativa.
</Note>

### ResetPassword — `/reset-password`
**Arquivo:** `src/pages/AuthPages/ResetPassword.tsx`

Fluxo de 4 passos controlado por `useState<Step>` (`"email" | "code" | "password" | "success"`), sem roteamento próprio:

1. **email** — usuário informa e-mail (pré-preenchido se já logado); chama `requestPasswordReset(email)` do `useAuth`.
2. **code** — usuário digita o código recebido; validação só de campo não-vazio (a validação real do código acontece no passo seguinte, via API). Permite reenviar.
3. **password** — nova senha + confirmação, com indicador de força (`getPasswordStrength`, calculado no cliente: comprimento, maiúscula, número, símbolo). Validações antes de enviar: mínimo 8 caracteres, 1 maiúscula, 1 número, confirmação igual. Chama `confirmPasswordReset(email, code, newPassword)`. Erro no código volta para o passo `code`.
4. **success** — confirmação; botão vai para `/` (logado) ou `/signin`.

- **Hooks:** `useAuth` (`requestPasswordReset`, `confirmPasswordReset`).
- **Estados:** `loading` por submit, `error` textual por passo.

### InstagramSuccess — `/app/instagram/success/:clientId/*`, `/app/linkedin/success/:clientId/*`, `/app/whatsapp/success/:clientId/*`
**Arquivo:** `src/pages/AuthPages/InstagramSuccess.tsx`

Tela de retorno do OAuth de redes sociais (as três rotas apontam para o mesmo componente; a rede é lida de `?connected=` ou, na ausência, inferida do próprio path). Antes de qualquer leitura de estado, chama `clearOnboardingCache()` (síncrono, fora de `useEffect`) para não reaproveitar cache de onboarding desatualizado pela conexão recém-concluída.

Usa `useOnboarding(clientId)` (`isInOnboardingFlow`, `loading`) para decidir o destino:
- Se ainda em onboarding: navega (`replace`) para `/onboarding/conectado/:platform/:clientId` (quando dá para identificar rede+cliente) ou `/onboarding?continuar=1`.
- Fora do onboarding: mostra botões "Voltar para o Perfil" (`/app/profile`) / "Ir para Conteúdos" (`/app/content`).

- **Hooks:** `useOnboarding`, `useParams`, `useSearchParams`.
- **Estados:** enquanto `loading || isInOnboardingFlow` é `true`, mostra só "Retomando a configuração…" (evita piscar os botões de saída).

### GridApprovalPage — `/grid/aprovar`
**Arquivo:** `src/pages/Grid/GridApprovalPage.tsx`

MIG-165. Tela que o cliente abre por link enviado no WhatsApp para aprovar o **estilo visual** (grid 3×3) gerado para a marca. Fica dentro de `ProtectedRoute` mas **fora** dos guards de onboarding/assinatura (exige só login).

- Ao montar, chama `fetchMyGridApproval()` e `onboardingApi.getPhotos()` (`src/hooks/useBrandkit.ts` / `src/services/onboardingApi.ts`) em paralelo. - `sendMyGridFeedback(texto)` registra pedido de ajuste (regeração acontece depois, por cron — não na hora).
- `approveMyGrid()` aprova o estilo; chama `clearOnboardingCache()` (o cache do onboarding pode ter ficado obsoleto) e, se houver `next`, navega para lá.

- **Estados:** `loading` inicial (spinner); `aguardandoGrid` quando o mosaico ainda não foi gerado (`generation_status === 'pending'` ou sem `image_url`) — mostra card de espera em vez do formulário; `error`/`info` textuais.
